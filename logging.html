Structured Logging
Without Allocating

Tutan Logging keeps records as typed data, not text. An event is declared once as a static partial method, and a source generator writes the method a program calls. Records are drained once a frame to the Unity Console, with a link to the line that wrote them, and to a JSON lines file. An error brings the records that led to it. A view reads a live store, or a session's file read back, as rows a filter query keeps, and the log console, an editor window beside Unity's Console, reads a session's records whole.

Basics

Quick Start

Debug.Log formats text at the call, allocates, captures a stack trace for every line, and keeps nothing a filter or a backlog can use. This package keeps records as typed data instead. An event that is off costs one compare. An event that is on copies its values into fixed rings and allocates nothing. Formatting waits for a reader: the Unity Console once a frame, a JSON lines file, or a test.

Install

Add the package and its one dependency to Packages/manifest.json:

manifest.json
{
  "dependencies": {
    "com.tutan.functional": "https://github.com/TutanDev/com.tutan.functional.git",
    "com.tutan.logging": "https://github.com/TutanDev/com.tutan.logging.git"
  }
}

Tutan.Logging is auto-referenced, so Assembly-CSharp sees it. An assembly with its own .asmdef adds Tutan.Logging to its references, and the generator runs on it from then on.

Declare an event

Events are declared in a top-level static partial class that names their category:

SaveLog.cs
using System;
using Tutan.Logging;

[LogCategory("game.save")]
internal static partial class SaveLog
{
    [LogEvent(LogLevel.Information, "Saved slot {Slot} in {Elapsed}")]
    static partial void Saved(int slot, TimeSpan elapsed);

    [LogScope(LogLevel.Information, "Saving slot {Slot}")]
    static partial void Saving(int slot);
}

A declaration has no body and no access modifier. Its parameters are the event's fields, and its template names them in holes. The generator writes, beside it, the method a program calls:

SaveLog.g.cs
// What the generator writes, in outline.
public static void Saved(this Log log, int slot, TimeSpan elapsed,
    [CallerFilePath] string callerFile = "", [CallerLineNumber] int callerLine = 0);

public static LogScope Saving(this Log log, int slot,
    [CallerFilePath] string callerFile = "", [CallerLineNumber] int callerLine = 0);

So log.Saved(3, elapsed) binds to the generated extension, and the compiler fills in the call site.

Write through a Log

Code that logs takes a Log, as it takes any other dependency:

SaveManager.cs
public sealed class SaveManager
{
    private readonly Log _log;

    public SaveManager(Log log) => _log = log;

    public void Save(int slot)
    {
        using LogScope saving = _log.Saving(slot);
        var watch = System.Diagnostics.Stopwatch.StartNew();
        // ...write the file...
        saving.Log.Saved(slot, watch.Elapsed);
    }
}

What is written through saving.Log is under the scope, and disposing saving writes the record that closes it, with how long it was open.

Test

A test hands the code a MemoryLog, which captures every level by default, and asserts on records as values:

SaveManagerTests.cs
using System.Linq;
using NUnit.Framework;
using Tutan.Logging;

public class SaveManagerTests
{
    [Test]
    public void Saving_says_the_slot()
    {
        using var logged = new MemoryLog();

        new SaveManager(logged.Log).Save(3);

        MemoryRecord saved = logged.Events.Single(r => r.Event == SaveLog.Events.Saved);
        Assert.That(saved.Field("Slot"), Is.EqualTo(3));
        Assert.That(saved.Scope, Is.Not.EqualTo(0));
    }
}

SaveLog.Events.Saved is the event's spec, which the generator writes into a nested Events class. Code that wants nothing logged is handed Log.Discard. A default Log was never handed a store, and its first event throws, so a forgotten dependency fails loudly instead of logging nowhere.

Basics

Composition Root

The composition root makes the store, the drain and its sinks, installs the pump and attaches the bridge. Each of those returns what undoes it, so the root owns teardown too. The code it composes receives a Log.

How the pieces fit
code ── log.Saved(3, file) ──▶ LogStore (fixed rings) ◀── LogPump stamps the frame (EarlyUpdate)
                                     │
                                     ▼  LogPump pumps the drain (end of PostLateUpdate)
                                 LogDrain ──▶ UnityConsoleSink   (rows with links)
                                     │──────▶ LogConsoleSink     (the log console's sessions ──▶ Window > General > Log Console)
                                     │──────▶ JsonLinesSink      (a file per session)
                                     └──────▶ MemorySink         (tests)

Debug.Log ── UnityLogBridge ──▶ LogStore

One way to write it

How the root is reached, and how a MonoBehaviour receives its Log, is the application's choice; the package ships no locator.

GameRoot.cs
using System;
using System.Collections.Generic;
using Tutan.Functional;
using Tutan.Logging;
using UnityEngine;

public sealed class GameRoot : MonoBehaviour
{
    private readonly List<IDisposable> _teardown = new List<IDisposable>();

    private void Awake()
    {
        LogRules rules = LogRules.Parse("debug; game.save=trace").Match(
            error => { Debug.LogWarning($"Log rules: {error.Message}"); return LogRules.Default; },
            parsed => parsed);
        var store = new LogStore(rules);

        var sinks = new List<(ILogSink, LogSinkOptions)>
        {
            (new UnityConsoleSink(), new LogSinkOptions(LogLevel.Information, Backlog: 20)),
        };
        LogFile.Session(store).Match(
            error => Debug.LogWarning($"No log file: {error.Message}"),
            file => sinks.Add((file, new LogSinkOptions(
                LogLevel.Debug, Backlog: 100, Redact: LogRedaction.HomeFolder))));

        var drain = new LogDrain(store, sinks.ToArray());
        _teardown.Add(drain);
        _teardown.Add(LogPump.Install(drain));
        _teardown.Add(UnityLogBridge.Attach(store.Log));

        var saves = new SaveManager(store.Log);
        // ...hand saves, and store.Log, to what needs them...
    }

    private void OnDestroy()
    {
        for (int i = _teardown.Count - 1; i >= 0; i--)
            _teardown[i].Dispose();
    }
}

Teardown runs in reverse: the bridge detaches, the pump leaves the PlayerLoop, and the drain writes what is left and closes the file.

Version 2 Version 2 reads records as well as writing them. A LogView shows what a LogFilter keeps, over a live store or a LogArchive read back from a session's file. A LogConsoleSink keeps every record of a session, whole, in LogConsole.Sessions, and a session that ended stays until the console is cleared. The log console, an editor window beside Unity's Console, draws them. A runtime overlay, actions on a field's value and reading a player's log remotely are not in this version.
Basics

The Log Console

Add a LogConsoleSink to the drain, and open Window > General > Log Console:

GameRoot.cs
var drain = new LogDrain(store,
    (new UnityConsoleSink(), new LogSinkOptions(LogLevel.Warning)),
    (new LogConsoleSink(), new LogSinkOptions(LogLevel.Debug)));

The window shows a session's records as rows a query keeps, with a badge for each level and a tree of the categories. Selecting a row shows its fields, the scopes it is under, where it was written and the source around that line, and double-clicking it opens that line. A session that ended, as when Play Mode exits, stays until the console is cleared, and a session's JSON lines file can be opened and read back.

The team shares saved filters, category colours and what is always left out, in ProjectSettings, and each developer keeps their own columns, Clear on Play and Pause on Error, in UserSettings. Outside the editor the sink keeps nothing.

The window is on its own page, The Log Console; the sink and its sessions are in Log Console Sessions.

Events & Scopes

Declaring Events

An event is something a program says: a save written, a level loaded, a connection lost. It is declared once, and the generator writes the method a program calls.

The category class

SaveLog.cs
[LogCategory("game.save")]
internal static partial class SaveLog
{
    // declarations
}
  • The class is top-level, static, partial and not generic, because what the generator writes beside its declarations are extension methods of Log.
  • [LogCategory] names the category of every event the class declares: one or more lowercase words of letters and digits, each starting with a letter, joined by dots, as game.save.
  • A category is one class's. Two classes of one assembly declaring one category is a compile error (TLOG0009), and two assemblies doing it is a conflict the catalog reports at runtime.
  • The class's own accessibility holds the generated methods: an internal class keeps its events to its assembly.

The declaration

SaveLog.cs
[LogEvent(LogLevel.Information, "Saved slot {Slot} in {Elapsed}")]
static partial void Saved(int slot, TimeSpan elapsed);

A declaration is a static partial void method with no body and no access modifier. It is a signature the generator reads: C# allows a partial method without a body only when it has no access modifier and returns void. Its parameters are the event's fields, in the order the call writes them. A parameter is passed by value, with no default and no params, and a declaration never takes the Log, which the generator adds. The names Events and RegisterLogEvents are the generator's own, and a declaration cannot use them.

The key

An event's key is its category and its name, game.save/Saved, which is what rules, files and the catalog name it by. The name is the method's, unless the attribute gives one, which keeps the key when the method is renamed:

CombatLog.cs
[LogEvent(LogLevel.Information, "Struck", Name = "Struck")]
static partial void Strike();

A name is an ASCII letter or _, followed by letters, digits and _. Two events of one class with one key is a compile error (TLOG0004).

The level

LogLevel runs Trace, Debug, Information, Warning, Error, Critical. None is a threshold that nothing passes, and an event cannot be declared at it.

Most events have one level, given by the attribute. An event whose level each call chooses, as for messages the program hears from elsewhere, leaves the level out of the attribute and takes exactly one LogLevel parameter, which is not a field:

NetLog.cs
[LogEvent("Heard {Message}")]
static partial void Heard(LogLevel level, string message);

log.Heard(LogLevel.Warning, "careful");

A rate limit

AiLog.cs
[LogEvent(LogLevel.Warning, "No path to {Target}", PerSecond = 5)]
static partial void NoPath(Vector3 target);

PerSecond is how many records of the event a store keeps a second, at most. The rest are counted, not kept, and the next record kept says how many were dropped before it. It answers a warning that fires every frame. 0, the default, is no limit, and a rule can override either way (see Rules & Rate Limits).

Fields & Templates

A value is copied into the store when it is logged, so a reader sees it as it was. A reference to anything but a string, which cannot change, or an exception would be read as it is when it is read, so other reference types are refused (TLOG0002). An event has at most 32 fields (TLOG0010).

Formatting a struct of the program's own type allocates the string its ToString returns, when a reader formats it, never at the call.

Field names

A field is named as the template's hole spells it, or, when no hole names it, as its parameter with the first letter made upper case. So Saved(int slot, string file) with the template Saved slot {Slot} has the fields Slot and File. Two parameters whose names differ only in case are refused, since a hole matches its parameter ignoring case.

Personal fields and tags

AccountLog.cs
[LogEvent(LogLevel.Information, "Signed in as {Email}")]
static partial void SignedIn([Personal] string email, [LogTag("path")] string folder);
  • [Personal] marks a field that can name a person. The store keeps it, and a sink whose options redact personal fields writes [personal] instead.
  • [LogTag] says what a field is beyond its type, for a reader that offers to act on it: a console that turns a field tagged asset into a button that pings the asset.

Templates

A template is the message, with holes that name fields:

HoleWrites
{Slot}the field Slot
{Slot,6}padded on the left to 6 chars
{Name,-6}padded on the right to 6 chars
{Ratio:0.00}with the format handed to the value's own formatting
{{ and }}a literal brace

A hole names a parameter, ignoring case, or the declaration is refused (TLOG0001). A template that does not parse, as an unclosed brace, is refused too (TLOG0007). A parameter no hole names is still a field: it is in the record, the file and the tests, just not in the message. Formatting is in the invariant culture, so a message reads the same on every machine.

Events & Scopes

Scopes

A scope is an operation with a beginning and an end, and the records written while it is open are under it. It is declared as an event is, with [LogScope], which always has a level, and the method the generator writes returns a LogScope.

SaveLog.cs
[LogScope(LogLevel.Information, "Saving slot {Slot}")]
static partial void Saving(int slot);

// At the call:
using LogScope saving = log.Saving(slot);
saving.Log.Saved(slot, elapsed);   // under "Saving slot 3"
  • Opening it writes a record with its fields, whose sequence becomes the scope's Id.
  • What is written through saving.Log is under the scope, and nothing else is, on any thread. There is no ambient state, so nothing is lost across an await or a UniTask continuation.
  • Disposing it writes the record that closes it, which says how long the scope was open. Disposing it twice, or disposing a copy, closes it once.
  • Scopes nest: a scope opened through saving.Log is under saving.
  • A scope that is off, because its event is off or a limit dropped it, has IsOn false and hands back the Log it was opened from. Disposing it does nothing.
Work that outlives the call Work that outlives the call that opened the scope is handed saving.Log, and whoever finishes the work disposes saving, so the closing says how long the whole took. A record written through the Log of a scope that has closed is still under that scope: the handle says which scope, and closing it cannot reach the copies.
Events & Scopes

Generated Code & Catalog

The generator runs on every assembly that references Tutan.Logging. A declaration it cannot write for is a compile error, listed in Generator Diagnostics.

What the generator writes

For each class, beside its declarations, one public static extension method of Log per declaration, with the declaration's parameters and two caller-info parameters:

SaveLog.g.cs
public static void Saved(this Log log, int slot, TimeSpan elapsed,
    [CallerFilePath] string callerFile = "", [CallerLineNumber] int callerLine = 0);
  • It checks whether the event is on, which is one compare, and if it is, copies the values into the store. It carries a doc comment pointing back at the declaration, since going to the definition of a call lands in generated code.
  • A nested public static class Events with one LogEventSpec field per declaration, named by the event: SaveLog.Events.Saved. A test compares a record's Event with it.
  • A registration method, run by [InitializeOnLoadMethod] in the editor and by [RuntimeInitializeOnLoadMethod(SubsystemRegistration)] in a player, so the catalog lists every event before any of them fires.

Caller-info parameters are optional parameters, and a partial method takes its parameter list from the declaration, so the generator cannot add them to it. That is why the generated method is the declaration's sibling, not its body. Generated parameters that would collide with a field are renamed, and C# keywords used as parameter names are escaped with @.

The catalog

LogCatalog lists every event and scope the process can say, filled as assemblies load. It is static because specs are metadata, as types are, and nothing is written through it.

MemberWhat it is
LogCatalog.EventsEvery spec registered, in the order of their indices
LogCatalog.CountHow many are registered
LogCatalog.Find(key)The spec with a key, as an Optional<LogEventSpec>
LogCatalog.ConflictsWhat two assemblies declared alike

Registering is idempotent, so registration can run on every entry to Play Mode, which it has to when domain reload is off, and still list each event once. A spec made again by the same class, after a domain reload, replaces the one with its key.

Two assemblies can declare what no compiler could catch:

  • LogCatalogConflict.KeyTwice: two events with one key. Both get an index and both are written, but Find keeps finding the first.
  • LogCatalogConflict.CategoryTwice: one category declared by two classes.

Every store also says each conflict as a record (log/KeyTaken, log/CategoryTaken), so it reaches the Console and the file.

A LogEventSpec says everything known about an event before it is written: Category, Name, Key, Kind, Level (none when each call chooses), Template, Fields, PerSecond, and Source, the assembly, class, file and line of the declaration.

Generator Diagnostics

The generator refuses a declaration it cannot write for with a compile error, and writes nothing for that class until it is fixed. Every diagnostic is an error, in category Logging, reported at the declaration, parameter or attribute at fault.

TLOG0001 - a hole names no parameter

Holes match parameters ignoring case, so {Slot} matches slot.

SaveLog.cs
[LogEvent(LogLevel.Information, "Saved slot {Slot}")]
static partial void Saved(int index);   // TLOG0001: no parameter named Slot

TLOG0002 - a type a field cannot hold

A field is a bool, char, number, decimal, Guid, DateTime, DateTimeOffset, TimeSpan, enum, string, Exception, ReadOnlySpan<char>, an unmanaged struct that implements IFormattable (as Vector3), or an Optional<T> or nullable of one of these but ReadOnlySpan<char>. Log what the program needs of an object, as its name or id, instead of the object.

A struct bigger than 256 bytes (LogField.MaxValueBytes) is not caught here, since its size is known only to Unity: making its spec throws ArgumentException when the class's events are registered.

TLOG0003 - not the shape the generator writes for

The message says which rule it breaks:

  • The class is nested, is not static, is generic, or is not partial.
  • The method is not a static partial method, has a body, has an access modifier, is generic, or returns something other than void.
  • The method is named Events or RegisterLogEvents, which the generator writes into the class.
  • A parameter is passed by ref, out or in, has a default, is params, or is a Log, which the generator adds.
SaveLog.cs
[LogEvent(LogLevel.Information, "Saved")]
public static partial void Saved();   // TLOG0003: an access modifier makes C# require a body

TLOG0004 to TLOG0010

  • TLOG0004: two events of one class have one key, the same method name or the same Name given in their attributes. Give one of them a Name of its own.
  • TLOG0005: a category, an event's name or a field's name is malformed. A category is lowercase words of letters and digits, each starting with a letter, joined by dots. An event's name, and a field's, is an ASCII letter or _ followed by letters, digits and _. Two parameters whose names differ only in case would be one field.
  • TLOG0006: an event declared at LogLevel.None; a negative PerSecond; an attribute that gives a level and a LogLevel parameter as well; or one that gives no level and no LogLevel parameter, or two LogLevel parameters.
  • TLOG0007: the template does not parse, as when a brace is not closed or a hole's alignment is not a number. A literal brace is written {{ or }}.
  • TLOG0008: an event is declared in a class with no [LogCategory], so it has no key.
  • TLOG0009: two classes of one assembly declare one category. Two assemblies doing it is caught at runtime instead, as a LogCatalogConflict.CategoryTwice and a log/CategoryTaken record.
  • TLOG0010: an event has more than 32 fields, which is more than a record holds.
Store & Rules

The Store

A LogStore is where a program's records are held. The composition root makes one, hands its Log to the code it composes, and owns it: the package never makes a store on its own. A process can have several, side by side, as two tests running at once do.

Stores.cs
var store = new LogStore(LogRules.Default);
var quiet = new LogStore(LogRules.Parse("warning").ValueUnsafe(),
    new LogStoreOptions(Records: 1024, Program: "Server"));

The rings

A store holds three rings of fixed size, allocated once:

RingHoldsDefaultLeast
RecordsOne 72-byte entry per record: its stamps, level, event, scope and call site16,38416 (LogStore.MinRecords)
BitsThe values copied at the call, in 8-byte slots65,536 slots32,768 (LogStore.MinBits)
RefsThe strings and exceptions kept by reference16,38464 (LogStore.MinRefs)

LogStoreOptions sets each size, which is rounded up to a power of two; a size below the least throws ArgumentOutOfRangeException. The defaults hold about 2 MB: some sixteen thousand records, a few frames' worth of a busy game or minutes of a quiet one. Capacity is how many records the store holds once rounded. LogStoreOptions.Program names the program, which a file sink writes first and names its file by; null reads Application.productName.

Writing

A record is written under a lock, held for the copy of its fields and nothing else: no user code and no allocation run under it. The timestamp is taken under the lock too, so sequences are in the order of time.

A writer never waits for a reader. When a ring is full the oldest records are overwritten, and since every reader reads by sequence, a reader that fell behind knows how many it lost. A drain that loses records says so, as a log/DrainFellBehind record and as a Lost call on each sink. The record that opened a scope still open is kept, however old it is, so whatever is written under the scope can still say what it is under.

Stamps

Every record carries:

StampWhat it is
SequenceFrom 1 in each store, with no holes; how every reader addresses a record
TimestampA Stopwatch timestamp, which the store's LogClock turns into a time
FrameThe frame the store was told last, by EnterFrame; 0 before the first
ScopeThe scope it was written under, or 0
ThreadThe managed id of the thread that wrote it
CallSiteThe file and line of the call, as the compiler filled them in
SuppressedHow many records of its event a limit dropped since the last one kept

LogPump calls store.EnterFrame(Time.frameCount) at the start of every frame (see Pump & Bridge). A store that is not pumped can be told its frame by whatever drives it. store.Clock holds when the store started, as LogClock(Started, StartedAt): Clock.At(timestamp) is the wall-clock time of a record, and LogClock.Between(from, to) is the time between two timestamps.

Reading

A sink never reads the store itself: a drain reads it and hands the sinks what it read. A reader of its own, as a console view, reads into a LogBatch:

Reader.cs
var batch = new LogBatch(records: 1024);
long next = store.First;

LogRead read = store.Read(next, batch);
for (int i = 0; i < batch.Count; i++)
{
    LogRecord record = batch[i];
    // ...
}
next = read.Next;
  • Read(from, batch) copies the records from a sequence on, as many as fit, and returns a LogRead that says the first copied, how many, the next sequence to read, and how many were Lost to overwriting after from.
  • Read(sequences, batch) copies the records of the given sequences the store still holds, in the order given; a scope's opening still open is found however old.
  • First is the oldest sequence the store still holds, and Next the one the next record gets.
  • A LogRecord is valid until the next read into its batch, and being a ref struct it cannot be kept past it.
Store & Rules

The Log Handle

A Log is what a program passes to the code that logs: a handle to one store, and to the scope what is written through it is under. It is a value of two words, so the Log of every scope a program opens allocates nothing.

MemberWhat it is
store.LogA handle under no scope
Log.DiscardA log that captures nothing: every event is off in it
log.IsHandedWhether it was handed a store
log.ScopeThe scope it writes under, or 0
log.IsEnabled(spec)Whether the event is on, which is what the generated method checks first
==, EqualsWhether two handles are to one store and one scope
A default Log throws on purpose A default Log was never handed a store, and the first event written through it throws InvalidOperationException, saying so. Code given no log fails loudly instead of logging nowhere, and code that wants nothing from a log is handed Log.Discard.

There is no static logger, no Log.Default, and no store that makes itself. Specs are static, in the catalog, because they describe the code that was compiled; records are not.

Store & Rules

Rules & Rate Limits

LogRules say what a store captures: a least level every event is held to, and rules that change it, or limit how often an event is kept, for the events a pattern names. A store compiles them with the catalog into one byte per event, which is all a call reads to decide it is off.

From text

Rules.cs
Result<LogRules> rules = LogRules.Parse(
    "debug; game.save=trace; ai.*=warning; game.input/Moved=off; physics/Contact=10/s");

Items are separated by ;, and spaces around them do not matter.

  • A bare level is the least. There can be one, and text with none keeps the default, debug.
  • pattern=what is a rule, where what is a level, off, a limit as 10/s, or a level and a limit separated by a comma, as debug,10/s.

Levels are trace, debug, information, warning, error, critical and off, ignoring case; info and warn are read too.

PatternNames
*Every event
gameThe category game
game.*game and every category under it, as game.save, but not gameplay
game.save/SavedOne event, by its key

Where two patterns match an event, the more specific wins: a key beats a category, a category beats every prefix, a longer prefix beats a shorter one, and every prefix beats *. Of two rules alike, the later wins. A level and a limit are resolved apart: a rule with only a limit keeps the level a less specific rule gave, and the other way round.

Parse fails with an Error whose Code is a LogRulesError:

CodeWhen
NotALevelA bare item, or what follows =, is not a level
NotAPatternA pattern is none of the four kinds
NotALimitA limit is not a whole number a second, or a rule has two
LeastTwiceA second bare level

rules.ToString() writes the text Parse reads back as the same rules.

In code

Rules.cs
var rules = new LogRules(LogLevel.Debug,
    new LogRule("game.save", LogLevel.Trace, F.None),
    new LogRule("physics/Contact", F.None, 10));

A LogRule is a Pattern, an optional Least (LogLevel.None for off) and an optional PerSecond. LogRules.Default is debug and no rules: a store captures what a developer would want when something goes wrong, and the sinks, which write from Information by default, write the rest only as an error's context.

Rate limits

A limit is a bucket per event that holds PerSecond records and refills at that rate, starting full. A record that finds the bucket empty is dropped and counted, and the next one kept carries the count as Suppressed. A rule's limit overrides the event's own PerSecond, and 0/s takes the event's limit away.

Changing them at runtime

DebugMenu.cs
store.Apply(LogRules.Parse("trace; ai.*=debug").ValueUnsafe());

Apply swaps the rules from any thread, and calls from then on read the new ones. It says, as a log/RuleMatchesNothing record, each rule whose pattern matches nothing the program declares, which is how a misspelt category is caught. store.Rules is the rules applied last. LeastFor(spec), PerSecondFor(spec) and MatchingNothing(specs) answer what the rules say of an event without a store.

What the log says about itself

The package declares its own events, in category log, so its trouble is in the same place as everything else's:

KeyLevelSays
log/DrainFellBehindWarning{Count} records were overwritten before the drain read them
log/SinkFailedErrorThe sink {Sink} failed, and is not written to again, with the exception
log/KeyTakenWarningTwo assemblies declare one key
log/CategoryTakenWarningTwo assemblies declare one category
log/RuleMatchesNothingInformationThe rule {Rule} matches no event the program declares

They are registered before any other event, and are held to the rules like any other: log=off silences them.

Sinks

Drain & Backlog

A sink is where records leave the program: the Unity Console, the log console, a file, or memory for a test. Sinks never read the store; a drain reads it and hands every record to each of its sinks, which write the ones their options let through.

Drain.cs
var drain = new LogDrain(store,
    (new UnityConsoleSink(), new LogSinkOptions(LogLevel.Information, Backlog: 20)),
    (file, new LogSinkOptions(LogLevel.Debug, Backlog: 100, Redact: LogRedaction.Personal)));

The drain

A LogDrain reads a store when it is pumped and hands what it read to its sinks, in sequence order, on the thread that pumps it. It has no thread of its own, since WebGL has none. It starts from the oldest record the store still holds, so what was logged before the drain was made is not lost.

MemberWhat it does
Pump()Reads what arrived since the last read, hands it to the sinks, and flushes them; throws ObjectDisposedException once disposed
Flush()Everything the store holds, to the sinks, now, on the caller's thread, and flushed: for a crash or an exit; does nothing once disposed
Dispose()Drains and flushes what is left, and disposes the sinks that are disposable
StoreThe store it reads

LogPump.Install(drain) pumps it once a frame from the PlayerLoop (see Pump & Bridge). An editor tool that wants records in Edit Mode, when the PlayerLoop does not run every editor frame, pumps it itself: EditorApplication.update += drain.Pump;.

The drain owns its sinks. A sink given twice is refused with ArgumentException, since it would write every record twice. A sink that throws is said, as a log/SinkFailed record with the exception, and is not written to again. The program and the other sinks go on.

Sink options

LogSinkOptions.cs
public sealed record LogSinkOptions(
    LogLevel Least = LogLevel.Information,
    int Backlog = 0,
    LogRedaction Redact = LogRedaction.None);

Least is the least level the sink writes. The store captures from Debug by default and sinks write from Information, so Debug records are there for a backlog without filling the Console.

Backlog

How many records below Least the sink writes before an error, as its context, at most. When a record at Error or Critical arrives, the sink is first handed the latest records it skipped that share the error's scope, oldest first, each marked as context.

  • The error's scope is its outermost known scope, so an error deep in nested scopes brings what happened anywhere in the operation it belongs to.
  • An error under no scope brings the latest records under no scope.
  • The opening of the error's scope is context too, so the sink can say what the error was under.
  • A scope's closing is never context: by the time the error arrives, it says only that something ended.
  • A record is written as context once, however many errors follow it.

0, the default, writes no backlog. A negative backlog is refused.

Redaction

What the sink leaves out of the fields it writes:

FlagWrites
LogRedaction.NoneEvery field as it was logged
LogRedaction.Personal[personal] for every field marked [Personal], exceptions included
LogRedaction.HomeFolder~ for the user's home folder, wherever a string, chars or exception field has it

The store keeps every value; redaction is per sink. A file that leaves the player's machine redacts what a developer's Console does not need to.

Sinks

Unity Console

UnityConsoleSink writes each record as one Console row, and in a player as one line of the player log.

Console row
new UnityConsoleSink(openOnDoubleClick: true, name: "unity console", callSiteLine: true)

// writes, for example:
[game.save] Saved slot 3 in 00:00:01.2000000  < Saving slot 3
SaveManager.cs:42  frame 1240
  • The first line is the category in brackets and the message, then (+N) when a limit dropped N records of the event before it, then < and the opening of the scope it is under.
  • A scope's closing reads Saving slot 3: done in 12.5 ms.
  • A record written as an error's context starts with (context) .
  • An exception follows its record whole, on the lines after it.
  • The second line is the call site, which in the editor is a link, <a href="Assets/Game/SaveManager.cs" line="42">, that opens the file at the line; then the frame, when the store had one. In a player it reads (at Assets/Game/SaveManager.cs:42). With callSiteLine: false a row is its first line alone, and in the editor, with openOnDoubleClick, a double-click still opens the call site.
  • Levels map to row types: Warning is a warning, Error and Critical are errors, and the rest are logs (UnityConsoleSink.TypeOf).
  • Records overwritten before the drain read them are a warning row, 1,234 records were overwritten before the Console read them.

A row is written with LogOption.NoStacktrace, since the stack Unity would capture is the drain's, not the call's. With openOnDoubleClick, in the editor, a row also opens its call site when double-clicked, through an internal Unity method; if a Unity version does not have it, every row is written with the public API and the link still opens the call site.

The bridge and the Console never feed each other The sink skips what UnityLogBridge captured from Unity's own log, which the Console already shows, and the bridge skips what this sink writes, so neither feeds the other. A row is a string, which Unity's log needs, so this sink allocates for every record it writes; records below its level cost nothing here.
Sinks

JSON Lines File

LogFile.Session(store, keep: 10) opens a file for this session in the Logs folder of Application.persistentDataPath, the folder a player build can always write. LogFile.Session(store, folder, keep) opens it in a folder of the program's choosing, which it makes if it has to.

GameRoot.cs
LogFile.Session(store).Match(
    error => Debug.LogWarning($"No log file: {error.Message}"),
    file => sinks.Add((file, new LogSinkOptions(LogLevel.Debug, Backlog: 100))));
  • The file is named for the program and the time the store started: Sample Game-20261101-102409-000.jsonl. Characters a file name cannot have become _.
  • The program's oldest files beyond keep, this one counted, are deleted; a file that cannot be deleted is left, and other programs' files are never touched.
  • It fails with an Error whose Code is a LogFileError: NoFolder when the folder cannot be made, NoFile when the file cannot.
  • A keep below 1 throws ArgumentOutOfRangeException.

new JsonLinesSink(stream, leaveOpen: false, name: "json") writes the same format to any stream.

The format

One JSON object per line, UTF-8 without a byte order mark:

Sample Game-20261101-102409-000.jsonl
{"format":1,"program":"Sample Game","started":"2026-11-01T10:24:09.0000000+01:00","redact":["Personal"]}
{"event":"game.save/Saved","id":1,"kind":"Event","lvl":"Information","template":"Saved slot {Slot} in {Elapsed}","fields":[{"name":"Slot","kind":"Int32","type":"int"},{"name":"Elapsed","kind":"TimeSpan","type":"System.TimeSpan"}],"source":{"assembly":"Assembly-CSharp","type":"Game.SaveLog","file":"C:\\Projects\\MyGame\\Assets\\Game\\SaveLog.cs","line":12}}
{"seq":4190,"scope":4182,"t":"2026-11-01T10:24:11.3510000+01:00","frame":1240,"thread":1,"lvl":"Information","key":"game.save/Saved","id":1,"msg":"Saved slot 3 in 00:00:01.2000000","file":"C:\\Projects\\MyGame\\Assets\\Game\\SaveManager.cs","line":42,"fields":{"Slot":3,"Elapsed":"00:00:01.2000000"}}
  • The header, first: format (JsonLinesSink.Format, now 1), program, started, and redact when the sink redacts.
  • A declaration, before the first record of each event: its key, an id numbered from 1 in each file, kind, lvl (absent when each call chooses), template, perSecond when it has one, its fields, and its source. A field has name, kind and type, and personal, tag, optional, names (an enum's members) and flags when they apply. So the file says what its records are without the program that wrote them.
  • A record: seq, scope when under one, t, frame when stamped, thread, lvl, key and the id of its declaration, msg, suppressed when a limit dropped some, context when written as an error's context, file and line when it has a call site, and its fields. A record names its declaration by id as well as its event by key, since two assemblies can declare one key.
  • A scope's opening has begin, its own sequence, and its closing has end, the opening's, and ms, how long it was open.
  • Numbers and bools are JSON's own, and a number that is not finite is a string. An exception is an object of its type, message and text. Every other value is its formatted text, and a value of the program's own type is formatted as the first hole that names it formats it.
  • {"lost":N} says N records were overwritten before the drain read them.

Its buffers are reused for each line, so writing allocates nothing once they have grown, but for an exception's text.

Sinks

Log Console Sessions

LogConsoleSink keeps a session for the log console: every record its drain hands it, whole and typed, in a live session of LogConsole.Sessions. The session starts when the drain opens the sink, and ends when the drain disposes it. An ended session stays until the console is cleared, so a Play Mode session can be read after Play Mode exits.

GameRoot.cs
var drain = new LogDrain(store,
    (new UnityConsoleSink(), new LogSinkOptions(LogLevel.Warning)),
    (new LogConsoleSink(), new LogSinkOptions(LogLevel.Debug)));
  • A session holds at most cap records, a million by default, and past that lets the oldest go a block at a time, which its Records.Dropped counts. So it keeps what was written since the last clear, not only what the store's rings still hold.
  • A record under a scope whose opening was below the sink's level is kept after that opening, so it still says what it is under. Such a scope's closing is below the level too, so the session shows the scope as open.
  • It keeps records whole, so its options redact nothing: options that do are refused when it is opened, and the drain says so as log/SinkFailed.
  • A sink keeps one session, so a sink given to a second drain fails there.
  • A sink that throws is written to no more, so its session ends then, as when its drain lets it go.
  • Outside the editor it keeps nothing, since no window can read a session, so a composition root can add it without an #if.
  • A cap below 1 throws ArgumentOutOfRangeException.

The sessions

LogConsole is the process's sessions.

MemberWhat it does
SessionsThe sessions, oldest first: a new read-only list each time one starts, ends, is opened, is closed or is cleared away
Find(id)A session's state now, by its LogSessionId, while it is one of them

A LogConsoleSession is Live, Ended (with At, when it ended) or File (with its Path and Skipped lines), and its Match takes a function for each. Every one has an Id and its Records, a LogArchive that a LogView reads as it reads a store (see Reading Records).

A session's state never changes in place: when a live session ends, Sessions is a new list with an Ended under the same id where it was. A domain reload lets every session go. The Log Console is the editor window that reads them.

Sinks

Tests & Custom Sinks

MemoryLog is a store that captures every level, unless given rules, drained into a MemorySink each time its records are read.

Memory, for tests

SaveManagerTests.cs
using var logged = new MemoryLog();
var saves = new SaveManager(logged.Log);

saves.Save(3);

MemoryRecord saved = logged.Events.Single(r => r.Event == SaveLog.Events.Saved);
Assert.That(saved.Field("Slot"), Is.EqualTo(3));
MemberWhat it is
LogThe handle to pass to the code under test
RecordsEvery record so far, scopes' openings and closings included
EventsThe events so far, without scopes' openings and closings
StoreThe store, for a test that reads it as a console would

A MemoryRecord has every stamp as a value (Sequence, Frame, Scope, Begin, Thread, Level, Kind, Event, Suppressed, Backlog, Elapsed, CallSite), its Message, and its Fields. record.Field("Slot") is a field's value by name, ignoring case: a number, bool, char, guid, date or span as itself, an enum as its long, text as a string, an exception as itself, and a value of the program's own type as its text.

MemorySink can be given to any drain, for a test that builds its own store; it also counts Overwritten records and Flushes. It allocates for every record, which is what a test wants and a program does not.

Writing a sink

ILogSink.cs
public interface ILogSink
{
    string Name { get; }
    void Open(LogContext context);
    void Write(LogRecord record, bool backlog, LogContext context);
    void Lost(long count, LogContext context);
    void Flush();
}
  • Open is called once, before anything else.
  • Write is called for every record the sink's options let through, and for each record of a backlog with backlog true.
  • Lost says how many records were overwritten before the drain read them, at that point in the sequence.
  • Flush makes what was written durable, as far as the sink can.
  • A sink that is also IDisposable is disposed with the drain.

A LogRecord is valid only during Write. A sink that keeps records copies what it needs out of it. LogContext is what a sink writes with:

MemberWhat it is
ClockThe store's clock, which turns a record's Timestamp into a time
ProgramThe program's name
Options, RedactThe sink's options
TryScope(scope, out begin)The record that opened a scope, if the drain read it and the scope has not closed
TryFormat(record, span, out written)The record's message with the sink's redaction, and for a scope's closing, its opening's message
Text(record)The same, as a string

A sink that wants to allocate nothing formats into a buffer of its own with TryFormat, and grows the buffer when it returns false. record.Field(i) and record.TryField(name, out value) return a LogValue, which reads as itself (Read<T>()), as a number (AsInt64(), AsDouble()), as chars (AsChars()), or as the reference it was kept by (AsRef()), and formats into a span (TryFormat).

Reading

Records a Reader Reads

A sink writes records out; a reader reads them as rows. A LogView is what a console reads: the records a filter keeps, kept up to date a frame at a time, with repeats counted rather than shown again and scopes drawn as a tree. It has nothing about drawing in it, so a test, an overlay and an Editor window read it alike.

A view reads a live LogStore, or a session held as a LogArchive, which LogFile.Read makes from the file a JsonLinesSink wrote. It asks both the same questions.

LogRecords is a store or an archive, and nothing else.

MemberWhat it says
Program, ClockThe program that wrote the records, and when its store started
EventsThe events the records are of: the catalog's for a store, the file's own declarations for an archive
CapacityThe most records it holds
First, NextThe oldest sequence it holds, and one past the newest
RedactedWhat the records lack, as the sink that wrote them left it out: None for a store, the file's for an archive
LateMark, LateFrom(seen)Where it is in placing records it was handed after a later one, and, as a LogLate, the least sequence placed late since the mark seen with the mark to pass next time
Read(from, into)Copies the records from a sequence on into a LogBatch, as a store's does
Read(sequences, into)Copies the records of the given sequences it holds

A store has no late records: its LateFrom is always Next. A LogLateMark is opaque: a reader keeps the one it was handed and passes it back. default, or a mark of other records, has seen none of these.

Reading

The View

A LogView shows what a LogFilter keeps, over a live store or a LogArchive read back from a session's file. Update reads what arrived since it last did, and drops the rows of records the store has since overwritten. It allocates nothing once its index has grown to the rows. A view is read and updated on one thread, as a console draws on one.

View.cs
LogFilter filter = LogFilter.Parse("level>=warning game.*").ValueUnsafe();
var view = new LogView(store, filter);

// Once a frame:
view.Update();
for (int row = 0; row < view.Count; row++)
{
    LogRow shown = view[row];
    // shown.Sequence, shown.Records, shown.Depth, shown.LostBefore...
}

Rows

LogRow.cs
public readonly record struct LogRow(long Sequence, long Last, int Records, long Suppressed, LogLevel Level,
    LogRowKind Kind, int Depth, long LostBefore);

A row is a record, or a run of records that repeat one another.

  • A repeat is a record of the same event, level, scope and values as the row before it, and is counted on that row. Records is how many, Sequence and Last the first and the last, and Suppressed adds up what a rate limit dropped among them. A run spans records the filter hides between them, but not a loss, and never joins a record written as an error's backlog to one that was not.
  • A scope's opening has a row of its own, LogRowKind.Scope, and what is under it is drawn under it: Depth is how many of the scopes a row is under have rows. A scope's closing has no row, since its opening's row says how long it was open (view.Scopes.Elapsed(scope)).
  • A loss is said on the row after it: LostBefore is how many records were lost just before that row, and view.Lost is all of them.

Find(sequence) is the row that holds a record, or the repeat whose run spans it, so a selection held by sequence keeps its row as the rows change.

Counts

Counts is how many records match, by level: everything the filter keeps but for its levels. So the count of a level is what keeping it would show, which is what a toolbar's level badges say. Counts.Total is all of them.

A new filter, and folds

Setting Filter to a filter not equal to the one it has scans every record held again, about sixteen thousand an update, into an index of its own. Setting an equal one does nothing. The rows stay as they were until the scan has caught up, and IsScanning says when one is under way. Until then, what the rows are asked is answered as the filter they were made with, Shown, says.

Fold(scope) hides what is under a scope and keeps the scope's own row, and Unfold(scope) shows it again. Each scans again, as a new filter does.

Clear() starts the view at the newest record, as if nothing came before it. The records are all still there.

Copying rows

Read(row, count, into) copies the record of each row into a batch, one a row. Write(sink, row, count) writes every record the rows stand for, each of a repeat's too, to a sink that has not been opened, as a drain would. A console copies rows as text or as JSON lines, or exports what it shows, through it.

Export.cs
using var file = new JsonLinesSink(File.Create(path));
view.Write(file, 0, view.Count);

Where the records say some were lost among them, or the store has overwritten some since, the sink is told how many.

Records placed late

An error's backlog reaches a sink after records with later sequences. An archive places such a record among the others by its sequence, and moves its LateMark on. When the mark has moved, the next Update reads the rows again from the first record placed late since, and only those, so the record shows where its sequence puts it.

Reading

Filters

A console's filter line is a query, which LogFilter.Parse reads and ToString writes back.

Filter line
level>=warning  game.*  -game.input/Moved  Slot:3  frame:1200..1300  scope:4182  "no image"  /fail(ed|ure)/

Terms

A query is words split by spaces. Each word is a term, or a term left out when it starts with -.

TermKeeps
level>=warningRecords at those levels; >, <=, <, = and : too, with a level as rules name it
frame:1200..1300Records of those frames; frame:1200.., frame:..1300 and frame:1240 too
scope:4182The scope and everything under it, on every thread it reached
thread:7What one managed thread wrote
File:*.pngRecords with a field of that name, ignoring case, whose formatted value the pattern matches, ignoring case; * is any text and ? any char
File:/\.(png|jpg)$/Records with a field whose formatted value a regular expression matches, ignoring case
@level:highA field named level, frame, scope or thread, which without the @ are the terms above
"no image"Records whose message holds the text, ignoring case
/fail(ed|ure)/Records whose message a regular expression matches, ignoring case
anything elseRecords of an event, as a rule names it: *, a category, category.*, or a key

A record is kept when its level and frame are in the ranges, it is of one of the events kept, if any are, it meets every other term kept, and it meets no term left out. So game.save game.load is either category, and game.* Slot:3 both.

Quotes and regular expressions

A value with a space in it is in quotes, in which \" is a quote and \\ a backslash. A regular expression is between slashes, in which \/ is a slash and every other backslash is the expression's own. A regular expression ignores case and culture, as quoted text and wildcards do.

A match that takes too long over a record gives up, and the record is not matched, so a pattern that backtracks without end cannot stall the editor. Over a view's rows, the term then matches nothing from that record on, rather than take as long over every record left: kept, it keeps nothing, and left out, it leaves nothing out. A record before that one is matched as before, when a record placed late has the rows read again, and a copy of the rows leaves out what the rows do. view.GaveUp says which terms did, in the filter's order, for a console to say under its filter line, and view.Retry() scans again to try them afresh. LogFilter.Matches alone remembers nothing, and tries every record afresh.

Parsing

Parse never throws for a query. It fails with the first word that is not a term, and a LogFilterError as the error's code: NotATerm, NotALevel, NotAFrame, NotAScope, NotAThread, NoText, NoValue, QuoteNotClosed, CannotLeaveOut, RegexNotClosed or NotARegex.

MatchingNothing(events) is the events and fields a filter names that no event is or has. A console says them under its filter line, since a word that is a category no event is of is more often text meant to be in quotes.

Filters as values

A filter is a value: two filters are equal when their levels, frames and terms are, and a view given an equal filter does not scan. A regular expression is its pattern: /a\/b/ and a term made from a/b are equal, and both write back as /a\/b/. A filter is also made from its parts, new LogFilter(levels, frames, keep, leaveOut), with LogLevelRange, LogFrameRange and the cases of LogFilterTerm.

Scopes

view.Scopes is what is under what, as the records the view has read say.

MemberWhat it says

Parent(scope)The scope it was opened under, or 0

A scope is the sequence of the record that opened it. Only the view teaches it, and asking it changes nothing, so a filter asks the same question twice and gets the same answer.

Reading

Reading a Session's File

LogFile.Read reads back a log a JsonLinesSink wrote, as far as it goes, so a session that is still writing its file is read up to its last whole line. It opens the file shared, so the session writing it, and the folder keeping its latest few, go on.

Result<LogSessionFile> read = LogFile.Read(path);

LogFile.Read(stream, name) reads a stream instead, from where it is to its end, and leaves it open.

Errors

LogSkipReasonThe line

What a file reads back as

The archive's events are the file's declarations, not the catalog's, so it reads a log whatever program wrote it. They are the file's alone: the catalog never holds one, a store's IsEnabled says no to one, and writing one throws. A record keeps its sequence, its stamps, its call site and its time.

A field reads back as the kind it was declared as, but for three the file holds only as text, which read back as strings:

  • a char or ReadOnlySpan<char>,
  • a value of the program's own type, such as a Vector3,
  • a field marked [Personal] in a file written with personal fields left out, which reads [personal].

An exception reads back as an ArchivedException: its TypeName is the full name it was thrown as, its Message is its message, and its ToString() is the text the file holds, stack trace and all.

The sequences have holes where the sink skipped records below its level. A read says records were lost only where the file says so.

The archive holds what the file held, and takes nothing after. Its Redacted is what the file's sink left out, and a view writing its rows to another sink leaves that out too, whatever the sink's own options, since the records no longer have it.

Unity

Pump & Bridge

The store, the rules and the drain know nothing of Unity's frame. Four pieces connect them to it: the pump, the bridge, the Console sink, and the registration the generator writes. Each piece the composition root installs returns what undoes it, so the root owns teardown too.

The pump

GameRoot.cs
IDisposable pump = LogPump.Install(drain);
// ...
pump.Dispose();

LogPump.Install adds two systems to Unity's PlayerLoop:

SystemWhereWhat it does
LogFrameStampFirst in EarlyUpdatestore.EnterFrame(Time.frameCount), so every record says the frame it was written in
LogDrainPumpLast in PostLateUpdateDrains the store to the sinks and flushes them, once the frame's work is done

Both show by those names in the Profiler. Disposing the pump takes out its two systems and no others, so several pumps can be installed, and disposing twice does nothing. A pump whose drain was disposed first does nothing, rather than throwing every frame.

Installed in Play Mode in the editor, the pump removes itself when Play Mode ends, since Unity keeps a PlayerLoop that was changed into Edit Mode. That also covers entering Play Mode with domain reload off: each entry installs a pump of its own, and nothing of the last one is left. In Edit Mode the PlayerLoop does not run every editor frame, so an editor tool pumps its drain itself: EditorApplication.update += drain.Pump;.

The bridge

GameRoot.cs
IDisposable bridge = UnityLogBridge.Attach(store.Log);
// ...
bridge.Dispose();

UnityLogBridge.Attach brings Unity's own log into a store, through Application.logMessageReceivedThreaded: every Debug.Log, warning, error, failed assertion and unhandled exception, from any thread. Each is a record of unity/Logged, with the fields Message, StackTrace and Type, at the level its type maps to:

LogTypeLevel
LogInformation
WarningWarning
Error, Assert, ExceptionError

So an exception Unity reports brings the records that led to it to a sink with a backlog, and code that does not log through a Log, as other packages', reaches the same file as code that does. Rules hold it like any other category: unity=warning keeps only Unity's warnings and errors.

  • The message and stack trace are kept by reference, so a message costs the store nothing Unity has not already allocated.
  • A bridged record has no call site: where Unity's log was called from is in its stack trace.
  • What UnityConsoleSink writes is not captured, and the sink does not write what the bridge captured, so the two never feed each other.
  • Attaching default throws ArgumentException, since it was never handed a store.
  • Attached in Play Mode in the editor, the bridge detaches itself when Play Mode ends, so a composition root that does not tear down still leaves nothing behind.

Registration

The generator writes, into every category class, a registration method marked with both [InitializeOnLoadMethod], so the editor registers the class's events when it loads the assembly, and [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)], so a player, and every entry to Play Mode, registers them before the first scene loads. Registering is idempotent, so entering Play Mode with domain reload off lists each event once. The package's own log and unity events are registered before any other.

Threads

A Log can be written from any thread: a record is written under the store's lock, which holds only for the copy of its fields. The drain and its sinks run on the thread that pumps it, which with LogPump is the main thread. UnityConsoleSink.Open asks Unity where the project and its packages are, which Unity answers only on its main thread, so a drain with a Console sink is made on the main thread.

Console Links & Builds

A record reaches the Console only when the drain writes it, so the stack Unity would capture is the drain's. The call site travels in the record instead: the generated method takes [CallerFilePath] and [CallerLineNumber], two values the compiler writes as constants, so a call still allocates nothing.

In the editor, a row written with openOnDoubleClick (the default) also opens the call site when it is double-clicked, as a Debug.Log written at that line does. Unity has no public way to say where a row opens, so this binds the internal Debug.LogInfo, LogWarning and LogError overloads that take a file and a line. It is kept apart from the sink, and Editor-only, so that a Unity upgrade that renames or removes them costs only the double-click: the sink falls back to rows with the link, for good, the first time binding or a call fails. new UnityConsoleSink(openOnDoubleClick: false) writes every row with the public API. new UnityConsoleSink(callSiteLine: false) leaves the link line out of every row, leaving the double-click as the way to the call site.

Caller paths in builds

The compiler writes each calling file's path into the assembly as a constant, once per file, and the generator writes each event's declaring file the same way. Unity's /pathmap:<project>=. covers only the assemblies of packages, so a package's file in the project reaches a build relative to it.

Assembly-CSharp and every assembly defined under Assets/ are compiled with no path map, so a build carries their files' absolute paths on the machine that built it, as C:\Projects\MyGame\Assets\Game\SaveManager.cs. So does a package whose folder is outside the project. Code that logs from an embedded package, a folder under Packages/, is compiled with Unity's path map like any other package's. A -pathmap in an assembly's csc.rsp maps the rest, though the option names the project's folder on one machine.

Absolute paths reach players A player knows no project folder, so it writes an absolute call site as the compiler wrote it, with forward slashes, as (at C:/Projects/MyGame/Assets/Game/SaveManager.cs:42).
