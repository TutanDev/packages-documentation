Optional<T>

Optional<T> represents a value that might exist (Some) or might be missing (None). It replaces null with explicit semantics and eliminates null-reference exceptions at API boundaries.

Creating Optional values

Use Some(value) to wrap a value, or None to represent absence. Both implicitly convert to Optional<T>. Some() treats destroyed Unity objects and null references as None automatically.

Example.cs
using static Tutan.Functional.F;

Optional<int> present = Some(42);
Optional<int> absent  = None;

// Implicit cast from T
Optional<string> name = "Alice";

// Returning None from a method
Optional<int> TryParseLevel(string raw)
{
    return int.TryParse(raw, out var level) ? Some(level) : None;
}

Transforming with Then()

Then() applies a function only when the value is Some, skipping over None automatically. Chain multiple Then() calls to build pipelines without nested null checks.

Pipeline.cs
Optional<Player> player = FindPlayer(id);

player
    .Then(p => p.Inventory)
    .Then(inv => inv.GetWeapon("sword"))
    .Match(
        onNone:  () => Log("No sword found"),
        onSome: sword => Equip(sword)
    );

Providing fallbacks

Use .Or(fallback) for an eager default or .OrElse(() => compute()) for a lazy one. Use .Filter(predicate) to convert a Some to None when a condition fails.

Fallbacks.cs
// Eager default
string label = playerName.Or("Guest");

// Lazy default (only computed if None)
Config cfg = maybeConfig.OrElse(() => Config.Default);

// Filter: keep only non-empty names
Optional<string> validName = rawName
    .Filter(s => s.Length > 0)
    .Then(s => s.Trim());

Pattern matching

Match(onNone, onSome) exhaustively handles both cases. It forces you to decide what to do in the absence case rather than silently returning null.

Match.cs
public Vector3 ResolveSpawn(Optional<Transform> maybeSpawn)
{
    return maybeSpawn.Match(
        onNone: () => _fallbackSpawn.position,
        onSome:  t => t.position
    );
}
Unity fake-null Unity's UnityEngine.Object equality overloads return true for destroyed objects even when the reference is non-null. Some() checks for this and returns None automatically. The check happens once, at creation — an optional over a Unity object is scope-local, valid only within the frame/method that created it. If one outlives that scope, call Alive() to re-check at point of use (see Unity Integration).

Result<T>

Result<T> represents the outcome of an operation — either Success(value) or Error. Use it when you need to explain why something failed, not just that it did.

Creating Result values

Creation.cs
using static Tutan.Functional.F;

Result<int> ok    = Success(42);
Result<int> fail  = Error("Value must be positive");

// Wrap exceptions automatically
Result<int> parsed = Try(() => int.Parse(rawInput));

// Filter: fail if predicate returns false
Result<int> positive = parsed.Filter(n => n > 0);

Chaining operations

Then() applies a function only on success. If any step returns an error, the rest of the chain is short-circuited — you handle the error once at the end with Match().

Pipeline.cs
// No null check needed: Try routes the value through Success,
// which turns null into Error("Value is null").
Try(() => JsonUtility.FromJson<PlayerConfig>(json))
    .Then(cfg => Validate(cfg))
    .Then(cfg => Save(cfg))
    .Match(
        onError:   e => Debug.LogError(e.Message),
        onSuccess: _ => Debug.Log("Config saved")
    );

Recovering from errors

.Or(fallback) and .OrElse(error => …) unwrap to a plain value. When you want to stay in Result space — recover into another Result<T>, or just observe the error and pass the original through — use .IfFail(…).

Recovery.cs
// Unwrap to a value — eager fallback
PlayerConfig config = LoadConfig(path)
    .Or(PlayerConfig.Default);

// Unwrap to a value — inspect the error first
PlayerConfig config2 = LoadConfig(path)
    .OrElse(err => {
        Debug.LogWarning(err.Message);
        return PlayerConfig.Default;
    });

// Stay in Result space — recover into another Result<T>
Result<PlayerConfig> recovered = LoadConfig(path)
    .IfFail(err => LoadConfig(backupPath));

// Or just observe the error and pass the Result through unchanged
LoadConfig(path)
    .IfFail(err => Debug.LogWarning(err.Message));

Void results (Result<Unit>)

When an operation succeeds or fails but carries no value, return Result<Unit>. Build it with Success() / Fail(...) and match it with a parameterless success branch. A Result<T> is also truthy on success, so if (result) reads naturally.

SaveScore.cs
using Tutan.Functional;
using static Tutan.Functional.F;
using Unit = System.ValueTuple;   // the package's Unit alias is internal to its own assembly

public Result<Unit> SaveScore(int score)
{
    if (score < 0)
        return Fail("Score cannot be negative");

    // ... persist ...
    return Success();
}

SaveScore(score).Match(
    onError:   e  => Debug.LogError(e.Message),
    onSuccess: () => Debug.Log("Saved"));   // no throwaway Unit argument

if (SaveScore(score))
    Debug.Log("Saved");
Optional vs Result Use Optional<T> when "not found" is a normal, expected state. Use Result<T> when failure needs an explanation — parsing errors, IO failures, validation failures.
Guides

The Error Type

Error is an immutable value type (24 bytes on 64-bit) that carries a message, an optional integer Code, and optional nested or composite inner errors. It is the failure payload inside Result<T>.

Simple error

SimpleError.cs
Error e1 = new Error("Save file not found");
// or via the F module helper:
Error e2 = Error("Save file not found");
// or implicitly from string:
Error e3 = "Save file not found";

// An Error converts implicitly to any Result<T>:
Result<SaveData> result = Error("Save file not found");
// Result<SaveData> bad = "Save file not found";  // does not compile:
// string → Error → Result is two user-defined conversions

Nested error — wraps a cause

Use nested errors to attach a high-level message to a lower-level cause — similar to Exception.InnerException.

Nested.cs
Error inner = Error("Disk read failed");
Error outer = Error("Could not load save", inner);

// outer.Message     → "Could not load save"
// outer.InnerErrors → [{ "Disk read failed" }]

Error with a code — attach a machine-readable code

The optional Code is an int (default 0 when unspecified). Use it when callers should branch on a stable code rather than parse the message — HTTP-style status codes, a domain error enum cast to int, and so on. Code participates in equality.

Coded.cs
Error e = Error("Save file not found", 404);

// Combined with a nested cause
Error outer = Error("Could not load save", 500, inner);

// e.Code → 404

Composite error — collects multiple failures

Pass a collection of errors to create a composite that joins all messages with "; ". This is what HarvestErrors produces when multiple validators fail simultaneously. AsEnumerable() flattens an error for logging: a composite yields its inner errors (one level, not recursive), while a simple or nested error yields { this }, so a nested error keeps its high-level message and you reach the cause through InnerErrors.

Composite.cs
Error composite = Error(new[] {
    Error("DisplayName is required"),
    Error("Level must be >= 1"),
    Error("Currency must be >= 0"),
});
// composite.Message → "DisplayName is required; Level must be >= 1; ..."

foreach (var e in composite.AsEnumerable())
    Debug.LogError(e.Message); // logs each error separately

Validation Pipelines

A Validator<T> is a function T → Result<T>. Combine validators with FailFast (stop at first failure) or HarvestErrors (collect all failures).

Validation.cs
using static Tutan.Functional.F;

Validator<PlayerConfig> hasName  = cfg =>
    cfg.DisplayName.Length > 0 ? Success(cfg) : Error("DisplayName required");

Validator<PlayerConfig> hasLevel = cfg =>
    cfg.Level >= 1 ? Success(cfg) : Error("Level must be >= 1");

// Stops at first failure
Validator<PlayerConfig> fast     = FailFast(hasName, hasLevel);

// Runs all validators, collects all errors into a composite
Validator<PlayerConfig> harvest  = HarvestErrors(hasName, hasLevel);

harvest(config).Match(
    onError:   e => Debug.LogError(e.Message),
    onSuccess: c => Apply(c)
);
// On failure, e.AsEnumerable() yields one Error per failing validator
// (a validator that itself returns a composite contributes each of its parts).
Which combinator, and where Prefer HarvestErrors at startup or in editor tooling, where showing every problem in one pass saves iteration time. Prefer FailFast in user-facing interactions where only the first error matters; it also skips the remaining validators. Neither is allocation-free (closures, LINQ, and the error list are allocated per call), so keep validation out of per-frame code.

Async Support

The core operators on Optional<T> and Result<T> (Map, Bind, Then, Match, Try) have async counterparts built on UniTask, so async pipelines look structurally identical to sync ones. Mix sync and async steps freely - the types handle the adaptation.

UniTask is optional The core library (Optional<T>, Result<T>, Error, validation, utilities) compiles without UniTask. The async surface on this page compiles only when the TUTAN_UNITASK scripting define is set. Installing UniTask as a UPM package (com.cysharp.unitask, via Git URL or OpenUPM) sets it automatically through the assembly definition's Version Defines. If you copied UniTask into Assets/ (e.g. from the .unitypackage release), Version Defines can't see it, so add TUTAN_UNITASK yourself in Project Settings › Player › Scripting Define Symbols.

Why UniTask, not Task<T>

Unity installs a UnitySynchronizationContext, so a Task awaited on the main thread resumes there. But continuations run on thread-pool threads when the await starts off the main thread or uses ConfigureAwait(false), and touching UnityEngine objects there throws UnityException. Task also allocates per operation. UniTask continuations are struct-based, low-allocation, and resume on the Unity player loop.

Async pipelines

Use TryAsync at every async boundary that might throw, ThenAsync to keep chains flat, and the sync Then overloads on UniTask<…> to interleave cheap synchronous steps. Any step that returns an error skips the rest. Always await the final UniTask - forgetting to await silently swallows errors.

AsyncPipeline.cs
// Chained async operations with error short-circuit
public async UniTask<Result<LeaderboardEntry>> FetchTopScoreAsync(string playerId)
{
    return await TryAsync(() => FetchPlayerAsync(playerId))
        .ThenAsync(player => FetchScoreAsync(player.Id))
        .ThenAsync(score => BuildLeaderboardEntryAsync(score));
}

// Mixed sync and async steps in one chain
Optional<Enemy> result = await Some("Prefabs/Boss")
    .ThenAsync(LoadPrefabAsync)                    // async: UniTask<Optional<GameObject>>
    .Then(go => go.GetComponent<Enemy>())          // sync:  UniTask<Optional<Enemy>>
    .Then(e => Debug.Log($"Spawned: {e.name}"));  // side-effect: passes the optional through

UniTaskF - closure-free Void and WaitUntil

UniTaskF (namespace Tutan.Functional) provides state-passing counterparts of two UniTask built-ins, so hot-path launches and polling stay closure-free. Void launches fire-and-forget work with 2-5 explicit arguments instead of a capturing closure; WaitUntil hands its predicate the state as an argument.

HitFlash.cs
// No closure: `this` and `damage` travel as arguments
UniTaskF.Void(static (self, dmg) => self.FlashAsync(dmg), this, damage);

// No closure: poll a field via state
await UniTaskF.WaitUntil(static hp => hp.Current <= 0, healthComponent, cancellationToken: token);

Unlike UniTask's WaitUntilValueChanged, the state in WaitUntil is held strongly (no WeakReference); tie the wait to the object's lifetime with a CancellationToken such as this.GetCancellationTokenOnDestroy().

Migrating from before 1.0.0 These helpers used to be UniTask.Void / UniTask.WaitUntil, injected into UniTask's own assembly through an .asmref. That couldn't be made conditional on UniTask being installed, so they moved to UniTaskF with the same signatures. Migrate by renaming the receiver.

Unity Integration

Unity-specific extension methods in LookupExtensions provide safe component access, parent traversal, and dictionary lookups that return Optional<T> instead of null.

Component lookup

HealthReader.cs
using Tutan.Functional;

public class HealthReader : MonoBehaviour
{
    [SerializeField] private GameObject target;

    private void Start()
    {
        int hp = target
            .LookupComponent<Health>()
            .Then(h => h.Current)
            .Or(0);

        Debug.Log($"HP: {hp}");
    }
}

Safe dictionary access

ItemLookup.cs
Optional<ItemDefinition> item = _itemTable.Lookup(itemId);

item.Match(
    onNone: () => ShowToast("Item not found"),
    onSome: def => ShowItem(def)
);

Object lifetimes: the scope-local rule

Optional<T> is an immutable snapshot — Some checks Unity's fake-null once, at creation and does not track the object afterwards. If the wrapped UnityEngine.Object is destroyed later, the optional still reports IsSome == true. So treat an optional over a Unity object as scope-local: valid only within the frame/method that created it. When one has to live longer, either re-lift at point of use (store the raw reference and call LookupComponent<T>() where you consume it) or re-check with Alive() — the monadic analogue of if (obj).

Lifetimes.cs
Optional<GameObject> cached = Some(enemy);
Object.Destroy(enemy);

// After the frame ends (Destroy is deferred):
Debug.Log(cached.IsSome);          // True  - the snapshot is stale
Debug.Log(cached.Alive().IsSome);  // False - Alive() re-checks Unity lifetime

// Holding an optional across frames? Alive() before consuming:
private Optional<Transform> _cachedTarget;

private void Update()
{
    _cachedTarget
        .Alive()                       // None if the target was destroyed
        .Then(t => Steer(t.position));
}

Alive() is constrained to T : UnityEngine.Object, so it doesn't exist (and costs nothing) for plain C# types — their snapshots can never go stale.

SerializableOptional<T>

Optional<T> is a readonly record struct — Unity's serializer cannot store it. SerializableOptional<T> is a [Serializable] wrapper that survives serialization and converts to and from Optional<T> implicitly. Like everything else, it lives in the Tutan.Functional namespace and runtime assembly.

Declare an inspector-friendly field

Add the field as SerializableOptional<T>, then convert it to Optional<T> as early as possible. Implicit casts work in both directions, so the field can be passed to any Optional<T> parameter. Implicit conversions don't apply to extension-method receivers, though: call .ToOptional() before chaining Then/Map/…

EnemySpawner.cs
using UnityEngine;
using Tutan.Functional;

public class EnemySpawner : MonoBehaviour
{
    [SerializeField] private SerializableOptional<Transform> overrideSpawn;
    [SerializeField] private SerializableOptional<int> startingWaveOverride;

    private void Start()
    {
        Vector3 spawn = overrideSpawn
            .ToOptional()
            .Then(t => t.position)
            .Or(transform.position);

        int wave = startingWaveOverride.ToOptional().Or(1);
    }
}

Inspector behaviour

SerializableOptionalDrawer is registered for the open generic SerializableOptional<>, so it applies to every closed SerializableOptional<T>. It implements UI Toolkit (CreatePropertyGUI) with an IMGUI fallback (OnGUI) for inspectors still drawn with IMGUI, and renders a row containing a toggle bound to the has value flag plus the inner value field, which is enabled only while the toggle is on. Inspector authors get a clear "use this value / leave it unset" UX without the wrapped value acting as a magic default.

Keep it at the serialization boundary Use SerializableOptional<T> only for [SerializeField] and ScriptableObject data, and keep the rest of the pipeline in terms of Optional<T>. Don't expose it from public APIs - it's a serialization concern, not a domain concern.
Assembly split SerializableOptional<T> ships in the Tutan.Functional runtime assembly; the drawer lives in Tutan.Functional.Editor. Add Tutan.Functional to your runtime .asmdef references — the editor assembly auto-loads in editor builds.

Performance & Hot Paths

This is an allocation-conscious library, not a zero-allocation one. Optional<T>, Result<T>, and Error are structs — creating, returning, and matching them never touches the heap. The fluent operators are only as free as the lambdas you pass them.

When pipelines allocate

A lambda that closes over a local or this allocates a closure object and a delegate every call. A lambda that captures nothing is cached by the compiler and allocates once, ever.

Closures.cs
// Allocates per call: the lambda captures `origin`
Optional<float> dist = maybeTarget.Map(t => Vector3.Distance(t.position, origin));

// No per-call allocation: nothing captured
Optional<Vector3> pos = maybeTarget.Map(t => t.position);

Hot-path options

System-level code — loading, validation, config, UI events — is the sweet spot; a closure allocation in code that runs once per click is irrelevant, so write for clarity. In per-frame hot paths (Update, physics callbacks, per-entity loops) you have three allocation-free options, in order of preference: keep lambdas capture-free, use the state-passing overloads, or exit the pipeline with the out-param accessors.

The state-passing overloads pass locals as an argument instead of capturing them. Map, Bind, Then, Filter, and Match all have TState forms on both Optional<T> and Result<T>, so a whole hot pipeline can stay capture-free end to end. Mark the lambdas static and the compiler enforces it.

HotPath.cs
// `origin` travels as TState — `static` guarantees no capture
float dist = maybeTarget
    .Alive()
    .Map(origin, static (t, o) => Vector3.Distance(t.position, o))
    .Match(float.PositiveInfinity, static d => d, static (v, _) => v);

// Need more than one local? Pack a value tuple — still no allocation
maybeTarget.Filter((minDist, origin),
    static (t, s) => Vector3.Distance(t.position, s.origin) > s.minDist);

// Or exit the pipeline and use plain control flow
if (maybeTarget.HasValue(out var target))
    Steer(target.position);
Two more gotchas Method-group arguments (.Map(GetPosition) with static Vector3 GetPosition(Transform t) => t.position;) also allocate a delegate per call under C# 10 - prefer an explicit capture-free lambda in hot paths. Try allocates when an exception is actually thrown (ex.ToString()); that's the exceptional path paying, which is the right trade.
