UP-Messages is a standalone, zero-GC message bus for Unity. Struct messages dispatched by ref, integer subscription tokens, thread-safe enqueue from worker threads — designed to survive 72–120 Hz XR frame budgets without dropping a frame.

Standalone package Messages ships independently of the rest of the Framework — com.tutan.messages has no dependencies beyond UnityEngine and Unity.Profiling, and is also available on the Unity Asset Store as a self-contained product.

Guides

Defining Messages

A message is any unmanaged struct implementing IEvent or ICommand (both extend IMessage). The unmanaged constraint guarantees no managed references — no string, no arrays, no class fields — making the struct blittable and invisible to the GC.

Correct messages

Messages.cs
using Tutan.Messages;
using Unity.Collections;
using UnityEngine;

// Correct — all fields are unmanaged
public struct HandTrackingLost : IEvent
{
    public int HandIndex;       // 0 = left, 1 = right
    public float Timestamp;
    public float Confidence;
}

// Use FixedString for string-like data
public struct SceneLoaded : IEvent
{
    public int SceneIndex;
    public FixedString64Bytes SceneName;
}

// COMPILE ERROR — string is a managed reference
public struct BadMessage : IEvent
{
    public string Name; // won't compile: not unmanaged
}
Need string-like data? Use Unity.Collections.FixedString64Bytes (from com.unity.collections) or store an integer handle that indexes into a separate lookup table. Both approaches keep the message blittable.

Events vs Commands

The bus exposes two static facades — EventBus for N:M notifications and CommandBus for N:1 intents. Picking the right one enforces CQRS rules at runtime.

TypeCardinalityNamingUse For
IEventN publishers, N subscribersPast tense — PlayerScored, OrderPlacedNotifying the world that something happened
ICommandN publishers, 1 subscriberImperative — MovePlayer, PlaceOrderRequesting that something be done

Command handlers are declared once at the composition root via CommandBus.TryInstall, each command type bound exactly once with .Handle<T>(…). That is the runtime enforcement of CQRS's "one writer per command" rule: a duplicate (or null) handler makes TryInstall return false with an error naming the offending type — it never throws.

Implementing the ICommandHandler<T> interface is the declarative way to state that a class handles command T. It is declarative only — it does not auto-register unless Auto-Install Command Bus is on. Even without that toggle, the interface makes handlers discoverable by the Commands authoring view (Project Settings → Tutan → Messages) which flags orphan and duplicate commands at edit time.

MovementManager.cs
using Tutan.Messages;

public sealed class MovementManager : ICommandHandler<MovePlayer>
{
    public void Handle(ref MovePlayer cmd) { /* ... */ }
}

// Composition root — Handle matches MessageHandler<T>, so it binds directly.
var movement = new MovementManager();
CommandBus.TryInstall(out var error, r => r.Handle<MovePlayer>(movement.Handle));

Subscribe & Unsubscribe

Subscribe returns a SubscriptionToken — an integer handle. Store it and pass it to Unsubscribe. There is no -= operator: this avoids the well-known fragility of delegate equality with lambdas and closures.

FadeController.cs
using Tutan.Messages;
using UnityEngine;

public class FadeController : MonoBehaviour
{
    SubscriptionToken _token;

    void OnEnable()
    {
        _token = EventBus.Subscribe<PlayerTeleported>(OnTeleported);
    }

    void OnDisable()
    {
        EventBus.Unsubscribe(_token);
    }

    void OnTeleported(ref PlayerTeleported msg)
    {
        StartFade(msg.Duration);
    }
}

The handler signature uses ref T — this eliminates the struct copy that Action<T> would force on every dispatch. Handlers may mutate the message (e.g., set a Consumed flag), and subsequent handlers will observe the mutation.

Publish & Enqueue

Publish dispatches immediately on the calling thread (main only). Enqueue is thread-safe and defers dispatch until DrainQueues() runs on the main thread. The auto-bootstrapped [MessagesHost] calls DrainQueues() in LateUpdate.

Immediate dispatch

TeleportSystem.cs
public class TeleportSystem : MonoBehaviour
{
    public void ExecuteTeleport(Vector3 origin, Vector3 dest, float duration)
    {
        var msg = new PlayerTeleported
        {
            Origin = origin,
            Destination = dest,
            Duration = duration
        };
        EventBus.Publish(ref msg);
    }
}

Queued dispatch from a worker thread

VideoStreamReceiver.cs
public struct FrameDecoded : IEvent
{
    public int FrameIndex;
    public int Width;
    public int Height;
    public long TimestampTicks;
}

public class VideoStreamReceiver
{
    // Called on a network/decode thread — NOT the main thread
    void OnFrameReady(int index, int w, int h)
    {
        var msg = new FrameDecoded { FrameIndex = index, Width = w, Height = h };

        // Enqueue is thread-safe. Dispatched on next DrainQueues() call.
        EventBus.Enqueue(msg);
    }
}

Commands — N:1 dispatch

OrderHandler.cs
public struct PlaceOrder : ICommand
{
    public int ItemId;
    public int Quantity;
}

// Handler — no Subscribe/Unsubscribe; just the method.
public class OrderHandler : MonoBehaviour
{
    public void Handle(ref PlaceOrder cmd)
    {
        ProcessOrder(cmd.ItemId, cmd.Quantity);
    }
}

// Composition root — declare every command handler in one place.
bool ok = CommandBus.TryInstall(out string error, r => r
    .Handle<PlaceOrder>(orderHandler.Handle));

if (!ok) Debug.LogError(error); // names the offending command type(s)

// Caller — same publish API
CommandBus.Publish(new PlaceOrder { ItemId = 7, Quantity = 3 });

Threading Model

Worker threads enqueue; the main thread drains and dispatches. The split lets you push messages out of network or decode threads without ever touching Unity APIs off the main thread.

APIThreadNotes
Publish / Subscribe / Unsubscribe / DrainQueuesMain thread onlyLock-free reads via ConcurrentDictionary<Type, ChannelBase>
EnqueueThread-safeLookup via ConcurrentDictionary.GetOrAdd; message lands in a per-channel ConcurrentQueue<T>
Always safe to touch Unity in handlers Even when the publisher was a background thread, the handler runs on the main thread — because DrainQueues() is called from LateUpdate. EventBus.Enqueue + handler is the idiomatic way to bridge worker results back to Unity APIs.

Auto-bootstrap & Scene Cleanup

Two pieces of startup work are usually needed before the bus is useful: something must call DrainQueues() every frame, and each command type needs its single handler bound through CommandBus.TryInstall. Both are opt-in and controlled from Project Settings → Tutan → Messages. The page writes the matching Scripting Define Symbols to the active build target so the same toggles apply in builds.

Auto-Install Drainers

Flip Auto-Install Drainers on (or define TUTAN_MESSAGES_AUTOINSTALL_DRAINERS) and MessagesBootstrap spawns a hidden persistent [MessagesHost] at BeforeSceneLoad. The host survives scene loads and calls DrainQueues() for both buses in LateUpdate.

With the toggle off, attach MessagesHost to a persistent GameObject yourself, or call EventBus.DrainQueues() / CommandBus.DrainQueues() from your own update logic (PlayerLoop callback, manager, etc.).

Auto-Install Command Bus

Flip Auto-Install Command Bus on (or define TUTAN_MESSAGES_AUTOINSTALL_COMMANDBUS) and MessagesBootstrap runs at AfterAssembliesLoaded: it scans every loaded assembly for concrete ICommandHandler implementations with a parameterless constructor, instantiates them, and for every closed ICommandHandler<T> they implement binds instance.Handle through a single CommandBus.TryInstall call.

If two handler types claim the same command, the N:1 rule turns it into one consolidated error logged at startup — the bus is left empty rather than partially installed. Handlers that need injected dependencies (services, scene refs, etc.) the discovery scan can't supply should be bound manually instead — leave this toggle off and do it at your composition root.

Scene transition cleanup

Reset the buses before unloading to clear stale subscriptions from destroyed MonoBehaviours:

SceneLoader.cs
public class SceneLoader : MonoBehaviour
{
    async void LoadScene(string sceneName)
    {
        EventBus.Reset();
        CommandBus.Reset();

        await SceneManager.LoadSceneAsync(sceneName);
        // New scene's OnEnable calls will re-subscribe.
    }
}
Guides

Editor Tooling

Editor-only instrumentation for inspecting bus traffic, plus inspector-friendly serialized wrappers for wiring messages without writing publisher code. Every instrumentation hook is gated behind [Conditional("UNITY_EDITOR")] and [Conditional("TUTAN_MESSAGES_DEBUG")] — the C# compiler strips all call sites in release player builds.

Messages Console

Open Window → Tutan → Messages Console for a virtualized log of recent Subscribe, Unsubscribe, Publish, Enqueue, and (optionally) drain operations with timestamp, frame, bus (E/C), op, and type. Selecting a row shows the message type, its payload, and — for Publish/Enqueue rows — the subscribers captured at the moment the message was sent.

Toolbar: Pause, Clear, Events / Commands toggles, per-op toggles (Publish / Enqueue / Subscribe·Unsubscribe / Drain), and a full-type-name search field. Drain records are off by default because they are noisy. While the window is open, struct payloads are boxed into records automatically so they can be inspected (one allocation per Publish/Enqueue); this is on whenever the window is open and incurs no cost once it is closed.

Commands authoring view

Embedded in the Messages settings page is a static, edit-time audit of the command → handler routing table. It lists every ICommand struct found via TypeCache as a card and resolves its handler(s) through ICommandHandler<T>; the command and each handler render as clickable ScriptFileField rows (single-click pings the .cs, double-click opens it).

A card is flagged when a command has no handler (orphan) or more than one (an N:1 violation). Toolbar: a name search, an Only warnings filter (persisted in EditorPrefs), and a Refresh re-scan. The view doubles as a sanity check for what will be installed when Auto-Install Command Bus is on.

Enabling in development builds

In the editor the console is always available (UNITY_EDITOR is always defined). To capture on-device in development player builds, flip Enable Instrumentation on in Project Settings → Tutan → Messages — it writes the TUTAN_MESSAGES_DEBUG define to the active build target.

When the console window is closed, MessagesInstrumentation.Enabled is set to false and every hook short-circuits on the first branch — so even with the define present, an empty/closed window costs roughly one bool check per Publish. With the toggle off, every [Conditional] call site is stripped at compile time and the ~256 KB record ring buffer is never allocated.

Programmatic access

MessagesInstrumentation is public and can drive custom diagnostics or in-game overlays:

DiagnosticsOverlay.cs
MessagesInstrumentation.Enabled = true;
MessagesInstrumentation.CapturePayloads = true;

// Snapshot the ring buffer (allocates a copy; keep off the hot path).
var records = MessagesInstrumentation.Snapshot();
foreach (var r in records)
    Debug.Log($"{r.Bus} {r.Op} {r.MessageType?.Name}");

Inspector-serializable references

EventReference and CommandReference are serializable wrappers that let designers pick a message type and edit its payload directly in the Inspector — useful for hooking up UnityEvents, prototyping, or wiring data-driven triggers without writing publisher code.

TriggerZone.cs
using Tutan.Messages;
using UnityEngine;

public class TriggerZone : MonoBehaviour
{
    [SerializeField] EventReference   onEntered;   // dropdown of all IEvent structs
    [SerializeField] CommandReference onActivate;  // dropdown of all ICommand structs

    void OnTriggerEnter(Collider other)
    {
        onEntered.Publish();   // boxes + reflection — fine for a one-shot trigger
        onActivate.Publish();
    }
}
Not for runtime hot paths. Publishing via a MessageReference involves JsonUtility.FromJson, Activator.CreateInstance, boxing the struct, and a reflected generic Publish invocation — the opposite of the zero-alloc dispatch path. Use it for editor/authoring workflows, debug buttons, and tooling — not per-frame gameplay dispatch.

The [EventType] / [CommandType] attributes

If you only need the type (not a payload), decorate a string field with [EventType] or [CommandType] to get a dropdown that stores the selected AssemblyQualifiedName. Resolve at runtime with Type.GetType(eventType).

TypePicker.cs
[EventType]   public string eventType;    // dropdown of all IEvent types
[CommandType] public string commandType;  // dropdown of all ICommand types

The inline reflection editor renders int, float, bool, string, Vector3, Color, and any enum. A field literally named Timestamp is skipped by the editor and auto-populated at publish time (float → Time.time, double → (double)Time.time, long → DateTime.UtcNow.Ticks).

Performance & Edge Cases

Every operation on the dispatch hot path is zero-allocation and amortized O(1) or O(n) in subscriber count. Pre-warm channels at startup to eliminate the initial growth of the backing List<T>.

OperationAllocationComplexityNotes
PublishZeroO(n) subscribersref dispatch, no delegate combine
EnqueueAmortizedO(1)Queue may grow; pre-warm to avoid
SubscribeAmortizedO(1)List.Add; one-time per subscription
UnsubscribeZeroO(n) subscribersLinear scan by token ID
DrainQueuesZeroO(channels × msgs)One dictionary iteration per frame
Channel lookupZeroO(1)Dictionary<Type, ChannelBase>

Pre-warming

Prewarm.cs
void Awake()
{
    // Force channel creation with a dummy subscribe/unsubscribe.
    EventBus.Unsubscribe(EventBus.Subscribe<HandGesture>((ref HandGesture _) => { }));
    EventBus.Unsubscribe(EventBus.Subscribe<FrameDecoded>((ref FrameDecoded _) => { }));
    // ... repeat for all message types used in the application
}
Reentrant publish, subscribe/unsubscribe during dispatch All three are safe. A depth counter ensures list compaction never runs while an outer dispatch is still iterating. Handlers added during dispatch will not see the current message; handlers removed during dispatch are skipped for the rest of the cycle. Exceptions in a handler are caught via Debug.LogException and dispatch continues.
