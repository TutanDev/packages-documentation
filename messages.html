UP-Messages is a standalone, zero-GC message bus for Unity. Struct messages dispatched by ref, disposable subscriptions, thread-safe enqueue from worker threads — designed to survive 72–120 Hz XR frame budgets without dropping a frame.

Guides

Defining Messages

A message is any struct implementing IEvent or ICommand (both extend IMessage). Dispatch is allocation-free for any struct: the bus is generic over the message type and passes it by ref, so the message is never boxed or heap-stored. Reference-type fields (string, arrays, collections, class payloads) are permitted — see the caveats below.

Defining message structs

Messages.cs
using Tutan.Messages;
using Unity.Collections;
using UnityEngine;

// Recommended — all fields are value types (no GC scan, safe across threads)
public struct HandTrackingLost : IEvent
{
    public int HandIndex;       // 0 = left, 1 = right
    public float Timestamp;
    public float Confidence;
}

// Use FixedString to keep string-like data value-typed
public struct SceneLoaded : IEvent
{
    public int SceneIndex;
    public FixedString64Bytes SceneName;
}

// Allowed, with caveats — reference-type fields are permitted
public struct LogLine : IEvent
{
    public string Text; // reference field: see the trade-offs below
    public int Level;
}
Reference-type fields are allowed but not free. A message that holds a string, array, collection, or class reference still dispatches without allocating, but two caveats apply: while it sits in the deferred queue it is a GC root the collector must scan during the mark phase (a scan cost, not an allocation), and Enqueue copies the struct shallowly, so a worker thread shares any referenced object with the main thread that drains it — treat such payloads as immutable handoffs. Prefer value-only messages on hot or cross-thread paths. For string-like data, Unity.Collections.FixedString64Bytes (from com.unity.collections) or an integer handle keeps the message fully value-typed.
Guides

Events vs Commands

The bus exposes two static facades — EventBus for N:M notifications and CommandBus for N:1 intents. Picking the right one enforces CQRS rules at runtime.

TypeCardinalityNamingUse For
IEventN publishers, N subscribersPast tense — PlayerScored, OrderPlacedNotifying the world that something happened
ICommandN publishers, 1 subscriberImperative — MovePlayer, PlaceOrderRequesting that something be done

Command handlers are declared once at the composition root via CommandBus.Install, each command type bound exactly once with .Handle<T>(…). That is the runtime enforcement of CQRS's "one writer per command" rule: a duplicate (or null) handler is reported in the returned InstallResult — Ok is false and Error names the offending type — and the live bus is left untouched. It never throws.

A command handler is just a plain method matching MessageHandler<T> (void Handle(ref T)) — no interface to implement, no base class. Any object can supply one: a MonoBehaviour, a plain C# manager, or a service from your DI container. Because you new them up yourself at the composition root, handlers are free to take whatever dependencies they need.

MovementManager.cs
using Tutan.Messages;

public sealed class MovementManager
{
    public void Handle(ref MovePlayer cmd) { /* ... */ }
}

// Composition root — Handle matches MessageHandler<T>, so it binds directly.
var movement = new MovementManager();
var result = CommandBus.Install(r => r.Handle<MovePlayer>(movement.Handle));

Subscribe & Subscription Lifetimes

Subscribe returns a disposable Subscription — disposing it is the one way to unsubscribe. There is no -= operator: this avoids the well-known fragility of delegate equality with lambdas and closures. Dispose() is idempotent, safe during dispatch, and a harmless no-op after the issuing bus was Reset().

Explicit handle — for dynamic lifetimes

Hold the Subscription in a field when the lifetime is genuinely dynamic, e.g. a view that subscribes in OnEnable and unsubscribes in OnDisable:

FadeController.cs
using Tutan.Messages;
using UnityEngine;

public class FadeController : MonoBehaviour
{
    Subscription _subscription;

    void OnEnable()
    {
        _subscription = EventBus.Subscribe<PlayerTeleported>(OnTeleported);
    }

    void OnDisable()
    {
        _subscription.Dispose();
    }

    void OnTeleported(ref PlayerTeleported msg)
    {
        StartFade(msg.Duration);
    }
}

.AddTo(this) — die with the GameObject

When a subscription should simply live and die with the component, skip the bookkeeping entirely: .AddTo(this) ties the Subscription to the GameObject (via one hidden SubscriptionAnchor component), and it is disposed automatically in OnDestroy. No handle field, no OnDestroy override:

FadeController.cs
public class FadeController : MonoBehaviour
{
    void Awake()
    {
        // Auto-unsubscribed when this GameObject is destroyed.
        EventBus.Subscribe<PlayerTeleported>(OnTeleported).AddTo(this);
    }

    void OnTeleported(ref PlayerTeleported msg) => StartFade(msg.Duration);
}

SubscriptionBag — one shared lifetime

For non-MonoBehaviour systems (or several subscriptions with one shared lifetime), collect them in a SubscriptionBag and dispose it once. The bag is reusable after disposal:

AnalyticsSystem.cs
public class AnalyticsSystem : IDisposable
{
    readonly SubscriptionBag _subscriptions = new();

    public AnalyticsSystem()
    {
        EventBus.Subscribe<PlayerTeleported>(OnTeleport).AddTo(_subscriptions);
        EventBus.Subscribe<PlayerScored>(OnScore).AddTo(_subscriptions);
    }

    public void Dispose() => _subscriptions.Dispose(); // unsubscribes both
}

Prefer .AddTo(this) when the subscription lives as long as the component, the bag for plain-C# systems, and an explicit handle field when the lifetime is genuinely dynamic. All three are the same Subscription underneath — and Subscribe allocates nothing beyond the handler entry itself.

The handler signature uses ref T — this eliminates the struct copy that Action<T> would force on every dispatch. Handlers may mutate the message (e.g., set a Consumed flag), and subsequent handlers will observe the mutation.

Publish & Enqueue

Publish dispatches immediately on the calling thread (main only). Enqueue is thread-safe and defers dispatch until DrainQueues() runs on the main thread. The auto-bootstrapped [MessagesHost] calls DrainQueues() in LateUpdate.

Immediate dispatch

TeleportSystem.cs
public class TeleportSystem : MonoBehaviour
{
    public void ExecuteTeleport(Vector3 origin, Vector3 dest, float duration)
    {
        var msg = new PlayerTeleported
        {
            Origin = origin,
            Destination = dest,
            Duration = duration
        };
        EventBus.Publish(ref msg);
    }
}

Queued dispatch from a worker thread

VideoStreamReceiver.cs
public struct FrameDecoded : IEvent
{
    public int FrameIndex;
    public int Width;
    public int Height;
    public long TimestampTicks;
}

public class VideoStreamReceiver
{
    // Called on a network/decode thread — NOT the main thread
    void OnFrameReady(int index, int w, int h)
    {
        var msg = new FrameDecoded { FrameIndex = index, Width = w, Height = h };

        // Enqueue is thread-safe. Dispatched on next DrainQueues() call.
        EventBus.Enqueue(msg);
    }
}

Commands — N:1 dispatch

OrderHandler.cs
public struct PlaceOrder : ICommand
{
    public int ItemId;
    public int Quantity;
}

// Handler — no Subscribe/Unsubscribe; just the method.
public class OrderHandler : MonoBehaviour
{
    public void Handle(ref PlaceOrder cmd)
    {
        ProcessOrder(cmd.ItemId, cmd.Quantity);
    }
}

// Composition root — declare every command handler in one place.
var result = CommandBus.Install(r => r
    .Handle<PlaceOrder>(orderHandler.Handle));

if (!result.Ok) Debug.LogError(result.Error); // names the offending command type(s)

// Caller — same publish API
CommandBus.Publish(new PlaceOrder { ItemId = 7, Quantity = 3 });

Threading Model

Worker threads enqueue; the main thread drains and dispatches. The split lets you push messages out of network or decode threads without ever touching Unity APIs off the main thread.

APIThreadNotes
Publish / Subscribe / Subscription.Dispose / DrainQueuesMain thread onlyLock-free reads via ConcurrentDictionary<Type, ChannelBase>. In the editor and development builds, off-thread calls log an error; release builds compile the check out
EnqueueThread-safeLookup via ConcurrentDictionary.GetOrAdd; the per-channel pending queue is lazily created with an Interlocked.CompareExchange, and the message lands in a ConcurrentQueue<T>. Safe to race against any main-thread call and against concurrent Enqueue calls — including the very first Enqueue of a message type
Always safe to touch Unity in handlers Even when the publisher was a background thread, the handler runs on the main thread — because DrainQueues() is called from LateUpdate. EventBus.Enqueue + handler is the idiomatic way to bridge worker results back to Unity APIs.
One carve-out: Reset / Install Reset() (and CommandBus.Install) replaces the bus instance wholesale. A worker-thread Enqueue racing that swap can land its message in the discarded bus, where it is dropped along with the rest of the cleared state. Quiesce worker threads before resetting or re-installing — both are composition-root operations, not steady-state ones.
Guides

Auto-bootstrap

Two pieces of startup work are needed before the bus is useful: something must call DrainQueues() every frame, and each command type needs its single handler bound through CommandBus.Install. The first is automatic with zero configuration; the second is one explicit call at your composition root.

Queue draining (automatic)

At startup MessagesBootstrap always spawns a hidden, persistent [MessagesHost] GameObject at BeforeSceneLoad. It survives scene loads and calls DrainQueues() for both buses every LateUpdate. No prefab to drag in, no toggle, no setup.

If you would rather own the drain loop, define TUTAN_MESSAGES_NO_AUTO_HOST to suppress the auto-spawned host, then either attach MessagesHost to a persistent GameObject yourself, or call EventBus.DrainQueues() / CommandBus.DrainQueues() from your own update logic (a PlayerLoop callback, a manager, etc.).

Binding command handlers (explicit)

Command handlers are declared once, at your composition root, through CommandBus.Install. The N:1 rule is validated there and reported in the returned InstallResult — on a duplicate command type or a null handler, Ok is false, Error names the offender, and the live bus is left untouched (it never throws).

A handler is just a method matching MessageHandler<T> (void Handle(ref T)), so any object — a MonoBehaviour, a plain C# manager, a DI-resolved service — can supply one. Because you new them up yourself, handlers are free to take whatever dependencies they need; there is no discovery scan imposing a parameterless-constructor rule. Call Install again to rebuild the bus from scratch (composition-root semantics) — previously installed handlers are replaced wholesale.

Editor Tooling

Editor-only instrumentation for inspecting bus traffic, plus inspector-friendly serialized wrappers for wiring messages without writing publisher code. Every instrumentation hook is gated behind [Conditional("UNITY_EDITOR")] and [Conditional("TUTAN_MESSAGES_DEBUG")] — the C# compiler strips all call sites in release player builds.

Messages Console

Open Window → Tutan → Messages Console for a virtualized log of recent Subscribe, Unsubscribe, Publish, Enqueue, and (optionally) drain operations with timestamp, frame, bus (E/C), op, and type. Selecting a row shows the message type, its payload, and — for Publish/Enqueue rows — the subscribers captured at the moment the message was sent.

Toolbar: Pause, Clear, Events / Commands toggles, per-op toggles (Publish / Enqueue / Subscribe·Unsubscribe / Drain), and a full-type-name search field. Drain records are off by default because they are noisy. While the window is open, struct payloads are boxed into records automatically so they can be inspected (one allocation per Publish/Enqueue); this is on whenever the window is open and incurs no cost once it is closed.

Enabling in development builds

In the editor the console is always available (UNITY_EDITOR is always defined). To capture on-device in development player builds, add TUTAN_MESSAGES_DEBUG to Project Settings → Player → Scripting Define Symbols for the target platform.

When the console window is closed, MessagesInstrumentation.Enabled is set to false and every hook short-circuits on the first branch — so even with the define present, an empty/closed window costs roughly one bool check per Publish. With the toggle off, every [Conditional] call site is stripped at compile time and the ~256 KB record ring buffer is never allocated.

Programmatic access

MessagesInstrumentation is public and can drive custom diagnostics or in-game overlays:

DiagnosticsOverlay.cs
MessagesInstrumentation.Enabled = true;

// Payload capture is not a separate switch — while Enabled, every
// Publish/Enqueue record carries the boxed payload.

// Snapshot the ring buffer (allocates a copy; keep off the hot path).
var records = MessagesInstrumentation.Snapshot();
foreach (var r in records)
    Debug.Log($"{r.Bus} {r.Op} {r.MessageType?.Name}");

Inspector-serializable references

EventReference and CommandReference are serializable wrappers that let designers pick a message type and edit its payload directly in the Inspector — useful for hooking up UnityEvents, prototyping, or wiring data-driven triggers without writing publisher code.

TriggerZone.cs
using Tutan.Messages;
using UnityEngine;

public class TriggerZone : MonoBehaviour
{
    [SerializeField] EventReference   onEntered;   // dropdown of all IEvent structs
    [SerializeField] CommandReference onActivate;  // dropdown of all ICommand structs

    void OnTriggerEnter(Collider other)
    {
        onEntered.Publish();   // boxes + reflection — fine for a one-shot trigger
        onActivate.Publish();
    }
}
Not for runtime hot paths. Publishing via a MessageReference involves JsonUtility.FromJson, Activator.CreateInstance, boxing the struct, and dispatch through the non-generic PublishBoxed seam (one unbox inside the channel) — the opposite of the zero-alloc dispatch path. Use it for editor/authoring workflows, debug buttons, and tooling — not per-frame gameplay dispatch.
Mark referenced structs [Serializable]. The payload round-trips through JsonUtility, which only serializes plain structs carrying the [Serializable] attribute. A message struct without it still works on the bus, but its payload cannot be edited through a reference — the values silently stay at their defaults.

The [EventType] / [CommandType] attributes

If you only need the type (not a payload), decorate a string field with [EventType] or [CommandType] to get a dropdown that stores the selected AssemblyQualifiedName. Resolve at runtime with Type.GetType(eventType).

TypePicker.cs
[EventType]   public string eventType;    // dropdown of all IEvent types
[CommandType] public string commandType;  // dropdown of all ICommand types

The inline editor renders each field with its matching native UI-Toolkit control: int, long, float, double, bool, string, any enum, Vector2/Vector3/Vector4, Vector2Int/Vector3Int, Color, and Quaternion (edited as euler angles). Other types fall back to a disabled "unsupported type" label. Every field is authored explicitly — including a field named Timestamp; the reference publishes exactly the values you enter, with nothing populated implicitly at publish time.

Performance & Edge Cases

Every operation on the dispatch hot path is zero-allocation and amortized O(1) or O(n) in subscriber count. Pre-warm channels at startup to eliminate the initial growth of the backing List<T>.

OperationAllocationComplexityNotes
PublishZeroO(n) subscribersref dispatch, no delegate combine
EnqueueAmortizedO(1)Queue may grow; pre-warm to avoid
SubscribeAmortizedO(1)List.Add; one-time per subscription
Subscription.DisposeZeroO(n) subscribersLinear scan by internal id
DrainQueuesZeroO(channels × msgs)One dictionary iteration per frame
Channel lookupZeroO(1)Dictionary<Type, ChannelBase>

Pre-warming

Prewarm.cs
void Awake()
{
    // Force channel creation with a dummy subscribe/dispose.
    // The channel's internal List is allocated once. The per-channel
    // ConcurrentQueue is lazy — it is allocated on the first Enqueue call,
    // so pre-warm that separately if your app uses queued dispatch.
    EventBus.Subscribe<HandGesture>((ref HandGesture _) => { }).Dispose();
    EventBus.Subscribe<FrameDecoded>((ref FrameDecoded _) => { }).Dispose();
    // ... repeat for all message types used in the application
}
Reentrant publish, subscribe/dispose during dispatch All three are safe. A depth counter ensures list compaction never runs while an outer dispatch is still iterating. Handlers added during dispatch will not see the current message; subscriptions disposed during dispatch are skipped for the rest of the cycle. Exceptions in a handler are caught via Debug.LogException and dispatch continues. Drains are bounded too: a handler that enqueues the same message type during dispatch extends the next frame's drain, not the current one, so a self-perpetuating handler cannot hang the frame.
