com.tutan.hosting · v0.1.0

A Composition Root
for Löwy's Method

You register your Managers, Engines, ResourceAccess, Resources and Utilities, and the host constructs them, hands each one its dependencies, installs them in dependency order and tears them down in reverse. Every constructor dependency is checked against the topology the Architecture validator reads, so an edge the validator would flag fails the install with a named error instead of running.

Quick Start

Something has to construct the Managers, Engines, ResourceAccess and Resources, hand each one its dependencies, start them in an order that works, and stop them in the reverse. This package is that place.

Install

Packages/manifest.json
{
  "dependencies": {
    "com.tutan.architecture": "https://github.com/TutanDev/UP-Architecture.git",
    "com.tutan.functional": "https://github.com/TutanDev/com.tutan.functional.git",
    "com.tutan.hosting": "https://github.com/TutanDev/com.tutan.hosting.git"
  }
}

Write a service

A hosted service carries the tag of its layer and implements IHostedService. The tag comes from com.tutan.architecture: a shorthand such as [Manager], the explicit [Layer(LayerId.Manager)], or [assembly: AssemblyLayer(LayerId.Manager)] for a whole assembly. IHostedService gives the host a way to start and stop the service.

NumberServices.cs
using System.Threading.Tasks;
using Tutan.Architecture;
using Tutan.Hosting;

[Engine]
public sealed class ValidatingEngine : IHostedService
{
    public bool IsValid(int value) => value >= 0;

    public ValueTask<InstallResult> InstallAsync() => new(InstallResult.Success());
    public void Remove() { }
}

[Manager]
public sealed class NumberManager : IHostedService
{
    private readonly ValidatingEngine _validating;

    public NumberManager(ValidatingEngine validating) => _validating = validating;

    public bool TrySet(int value) => _validating.IsValid(value);

    public ValueTask<InstallResult> InstallAsync() => new(InstallResult.Success());
    public void Remove() { }
}

Register it

Register services from a static method that runs at SubsystemRegistration, before the host builds. Registration order does not matter, because the host orders services by their dependencies.

AppInstaller.cs
using Tutan.Hosting;
using UnityEngine;

internal static class AppInstaller
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
    private static void Register() =>
        AppHost.Container
            .AddEngine<ValidatingEngine>()
            .AddManager<NumberManager>();
}

Await the install

AppHost builds and installs the registered services at BeforeSceneLoad, before the first scene's Awake. Scene code awaits the outcome and, on success, resolves its Manager and hands it to its Client.

AppBootstrap.cs
using Tutan.Functional;
using Tutan.Hosting;
using UnityEngine;

public sealed class AppBootstrap : MonoBehaviour
{
    [SerializeField] NumberClient _client;

    private async void Awake()
    {
        var installed = await AppHost.WaitForInstallAsync();
        installed.Match(
            onError: error => Debug.LogError($"[AppBootstrap] Install failed: {error}"),
            onSuccess: () => _client.Initialize(AppHost.Container.Resolve<NumberManager>()));
    }
}

The Client is an ordinary MonoBehaviour that Unity creates, so the host does not construct it. It carries [Client], so the validator checks that it calls one Manager, and it does not implement IHostedService, because nothing hosts it.

NumberClient.cs
using Tutan.Architecture;
using UnityEngine;

[Client]
public sealed class NumberClient : MonoBehaviour
{
    private NumberManager _manager;

    public void Initialize(NumberManager manager) => _manager = manager;
}

When it goes wrong

Give the Manager a second Engine and make one Engine call the other. Register it, and the install fails before anything is constructed. WaitForInstallAsync() returns the error, and the bootstrap above logs it.

PricingEngine.cs
[Engine]
public sealed class PricingEngine : IHostedService
{
    public PricingEngine(ValidatingEngine validating) { }

    public ValueTask<InstallResult> InstallAsync() => new(InstallResult.Success());
    public void Remove() { }
}
Console
[AppBootstrap] Install failed: 'PricingEngine' (Engine) depends on 'ValidatingEngine' (Engine) - violates Don't #11: Engines must not call other Engines.

The validator in com.tutan.architecture reports the same edge in the Editor as DONT011.

Guides

Registration & Tags

The container is opinionated in the way the Architecture validator is. Every service is a singleton, every dependency comes in through the one public constructor, and the Löwy topology decides which dependencies are allowed. There are no lifetimes, scopes or wiring strategies to choose.

MethodRegistersThe concrete type carries
AddManager<T>()a Manager[Manager]
AddEngine<T>()an Engine[Engine]
AddResourceAccess<T>()a ResourceAccess[ResourceAccess]
AddResource<T>()a Resource[Resource]
AddUtility<T>()a Utilityno layer tag

Every registered type implements IHostedService. Registration is fluent, so each call returns the container. Registering the same defining type twice throws, and so does registering once the build has started. There is no AddClient: Clients are MonoBehaviours that Unity creates, so the host never constructs them.

Interface mapping

Each method has an overload that registers an implementation under a defining type, usually an interface. A Manager can then take an IValidating in its constructor, and the container injects the ValidatingEngine. The service is registered under its defining type only, so a constructor that asks for ValidatingEngine itself finds nothing. The tag check reads the implementation, so ValidatingEngine is the type that carries [Engine].

AppInstaller.cs
AppHost.Container
    .AddEngine<IValidating, ValidatingEngine>();   // resolved and injected as IValidating

Layer tags are required

The tag is how the Architecture validator knows a type's layer, so the host requires it on every layered service and checks it against the registration. The tag can be on the type ([Engine] or [Layer(LayerId.Engine)]) or on its assembly ([assembly: AssemblyLayer(LayerId.Engine)]), and a type's own tag wins over its assembly's, as it does in the validator. A Utility carries no tag, which is the shape the validator already treats as a Utility.

Install errors
Missing layer tag: 'NumberManager' is registered as Manager but carries no [Manager] tag, so the editor validator cannot see it. Tag the type, or its assembly with [assembly: AssemblyLayer].

Layer mismatch: 'NumberManager' is registered as Engine but is tagged [Manager].
Every hosted service is a validated service A tag that disagrees with the registration fails the install, including a tagged type registered as a Utility. Because of this check, every service the host runs is also a service the validator checks.
Guides

Utilities

A Utility is not a layer. It is infrastructure from the vertical bar beside the layers, such as logging, security, diagnostics or a message bus. Löwy's test for one is the cappuccino machine: if a smart cappuccino machine could use it too, it is a Utility.

AppInstaller.cs
AppHost.Container
    .AddUtility<IClock, SystemClock>()
    .AddManager<NumberManager>();   // NumberManager can take an IClock

Any service may take a Utility as a constructor dependency, and a Utility may take other Utilities. A Utility may not take a Manager, Engine, ResourceAccess or Resource, because depending on one would tie it to this system's domain. The validator cannot see that edge, because it never tracks untagged types. The container can, because the registration says which services are Utilities.

Guides

Wiring & Enforcement

When the host builds, the container reads each service's public constructor. For each parameter it finds the service registered under the parameter's type, then checks the edge from the service to that dependency. An unregistered dependency, or an edge the architecture forbids, fails the install with an error that names the rule.

Between layers

The container allows exactly the edges the validator allows, because both read LowyTopology.

Every edge between layers points down, so only Utilities can form a cycle, and the container rejects one.

Guides

Lifecycle

Every service the host builds implements one interface, whatever its layer, Utilities included. The constructor wires and InstallAsync starts.

IHostedService.cs
namespace Tutan.Hosting
{
    public interface IHostedService
    {
        ValueTask<InstallResult> InstallAsync();
        void Remove();
    }
}
MethodPurpose
InstallAsync()Starts the service, after every service it depends on has started, and returns InstallResult.Success() or InstallResult.Failure(reason).
Remove()Stops the service: release resources, unsubscribe, clear state.

When a constructor runs, its dependencies have been constructed but not installed, so it should keep them and not call them. InstallAsync runs once every dependency has installed, so it can. It returns a ValueTask, so a service with nothing to await returns new(InstallResult.Success()) and allocates nothing. A service with real work to await makes InstallAsync an async method.

Two InstallResult types Tutan.Messages has an InstallResult of its own. A file that imports both namespaces writes Tutan.Hosting.InstallResult.

The host's timeline

AppHost ties the container to Unity's startup and shutdown.

WhenWhat happens
SubsystemRegistrationInstallers register services on AppHost.Container.
BeforeSceneLoadAppHost builds: it checks every tag and edge, constructs every service, then installs them in order.
The first scene's AwakeScene code awaits AppHost.WaitForInstallAsync() and resolves its Managers.
Application.quittingAppHost removes every installed service, in reverse install order.
Exiting Play Mode, in the EditorAppHost removes every service and starts the next session from an empty container.

The build starts at BeforeSceneLoad but does not have to finish there. A service whose InstallAsync awaits real work finishes later, which is why scene code awaits the outcome instead of assuming it. Registering after the build has started throws, so every installer runs at SubsystemRegistration.

Guides

Order, Rollback & Teardown

The container constructs every service, then installs them, in dependency order: each service comes after everything it depends on. Utilities come before every layered service, whatever order they were registered in.

Rollback

If a service's InstallAsync returns a failure, the container calls Remove() on every service that has already installed, in reverse order. The install then fails with the service's name and its reason.

Install error
Install failed for 'NumberAccess': the save file is locked.

The failed service is not removed, because it reported that it never started. Neither are the services after it, because they were never installed. After a failed install, Resolve keeps throwing, and the host does not try again.

Teardown

When the application quits, the host calls Remove() on every installed service, in reverse install order. Utilities install first, so they are removed last. A logger or a message bus is up before any layered service installs, and stays up until every one of them has been removed.

Guides

Awaiting & Resolving

AppHost.WaitForInstallAsync() returns a Task<Result<Unit>>. It returns the same Task to every caller, so every scene, and every bootstrap in a scene, can await it.

OutcomeResult
Every service installedA success, and Resolve works.
A tag, an edge, a dependency or an install failedA failure that carries the first error.
Called before BeforeSceneLoadA failure that says AppHost has not initialized yet.
A programmer error, such as two public constructorsThe task faults, and await rethrows the exception.

Awaited from a MonoBehaviour, it resumes on Unity's main thread. A project that uses UniTask can await the Task as it is, or call .AsUniTask() on it. AppHost logs a faulted install to the Console even when nothing awaits it.

Resolving services

Resolve<T>() returns the singleton registered under T, once the install has succeeded. Called before then, it throws and says to await AppHost.WaitForInstallAsync() first. It also throws for a type that is not registered.

Resolve is for the one place where Unity-owned code meets the host: handing a Manager to a Client. Services never call it, because they receive their dependencies through their constructors. A Client that needs a Utility gets it the same way.

Guides

Play Mode & Domain Reload

When Enter Play Mode Options skip the domain reload, static state survives from one Play session to the next.

AppHost removes every service and replaces its container when Play Mode exits, so each session starts empty and registrations do not pile up. The reset runs as the previous session ends, so it never races the next session's SubsystemRegistration installers.
