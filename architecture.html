Enforce Löwy's Method
at Compile Time

Tag types and assemblies with their layer and run validation, all without leaving the editor. The package enforces Löwy's closed, volatility-based architecture: five layers (Client → Manager → Engine → ResourceAccess → Resource), a fixed dependency topology, and the structural Design Don'ts. Tagging is all the validator asks of your code: no base class, no interface, no lifecycle methods.

Opinionated by design Internally the rules are data-driven and unit-tested, but the architecture they enforce is fixed: there is no layer, topology or rule configuration to edit, only how loudly violations are reported. The package has no dependencies and targets Unity 6000.1 and above.

The Five Layers

The layers are fixed, and their order is their volatility rank: Client is the most volatile, Resource the most stable. Dependencies flow from more volatile layers toward more stable ones, according to the topology.

RankLayerRoleSuffixGerund policy
0LayerId.ClientWhononenone
1LayerId.ManagerWhatManagerforbid
2LayerId.EngineHow (Business)Enginerequire
3LayerId.ResourceAccessHow (Resource)Accessforbid
4LayerId.ResourceWherenonenone

Client

The entry point to the system. Clients receive user input and call Managers to execute use cases. Under Löwy's Method a Client should call one Manager per use case, a topology cardinality cap reported as DONT001.

LobbyClient.cs
using Tutan.Architecture;

[Layer(LayerId.Client, Name = "Lobby Client", Description = "Handles lobby UI interactions")]
public class LobbyClient
{
    private readonly SessionManager _sessionManager;

    public LobbyClient(SessionManager sessionManager)
    {
        _sessionManager = sessionManager;
    }

    public void OnJoinPressed(string roomCode) => _sessionManager.JoinSession(roomCode);
}

Manager

The orchestrator of business logic. Managers coordinate Engines and ResourceAccess components to fulfill a use case.

SessionManager.cs
[Layer(LayerId.Manager, Name = "Session Manager", Description = "Orchestrates session lifecycle")]
public class SessionManager
{
    private readonly ValidatingEngine _validator;
    private readonly SessionAccess _sessionAccess;

    public SessionManager(ValidatingEngine validator, SessionAccess sessionAccess)
    {
        _validator = validator;
        _sessionAccess = sessionAccess;
    }

    public void JoinSession(string roomCode)
    {
        if (_validator.IsValidRoomCode(roomCode))
            _sessionAccess.Connect(roomCode);
    }
}

Engine

Performs a single activity or algorithm. Engines answer how: they encapsulate computation without knowing why or when it runs. An Engine must not call another Engine (DONT011), and its name should carry a gerund prefix (NAME002).

ValidatingEngine.cs
[Layer(LayerId.Engine, Name = "Validating Engine", Description = "Room code validation logic")]
public class ValidatingEngine
{
    public bool IsValidRoomCode(string code) => !string.IsNullOrEmpty(code) && code.Length == 6;
}

ResourceAccess

Abstracts access to external resources: databases, file systems, network endpoints, Unity asset bundles. A ResourceAccess must not call another ResourceAccess (DONT012). It is a terminal data layer, where a use case ultimately reads or writes its data.

SessionAccess.cs
[Layer(LayerId.ResourceAccess, Name = "Session Access", Description = "Network session connectivity")]
public class SessionAccess
{
    private readonly SessionConfig _config;

    public SessionAccess(SessionConfig config) => _config = config;

    public void Connect(string roomCode) { /* use _config to establish connection */ }
}

Resource

Raw data: ScriptableObjects, JSON schemas, configuration assets, external service contracts. Resources sit at the bottom of the volatility hierarchy, the other terminal data layer.

SessionConfig.cs
[Layer(LayerId.Resource, Name = "Session Config")]
public class SessionConfig
{
    public string ServerUrl;
    public int MaxPlayers;
    public float TimeoutSeconds;
}

Utilities are simply untagged

There is no [Utility] attribute. Only types that carry a layer attribute, or inherit one from [assembly: AssemblyLayer], are tracked, and the scanner only creates dependency edges between tracked types. A cross-cutting helper such as logging, serialization, math or the message bus participates in no edges as long as it is not tagged with a layer. To exempt a type, do not give it a layer.

Whole assemblies are also treated as transparent by name prefix and are never tracked, including System.*, UnityEngine.*, UnityEditor.*, Unity.* and Tutan.Functional.

The cappuccino machine test A type qualifies as domain-agnostic infrastructure if a smart cappuccino machine could use it too. If yes, leave it untagged. The companion package com.tutan.hosting registers such a type with AddUtility<T>(), and checks the one Utility rule the validator cannot: a Utility may depend only on other Utilities.

Tagging Your Code

A type joins the architecture through a layer attribute that names its layer. It needs no base class and no interface. The LayerId enum ships with the package, so the layers are compile-time safe.

Type-level attributes

Each layer has a shorthand attribute: [Client], [Manager], [Engine], [ResourceAccess] and [Resource]. They are thin LayerAttribute subclasses, so [Manager] is exactly [Layer(LayerId.Manager)]. Use the explicit form when you want to attach editor metadata.

InventoryManager.cs
using Tutan.Architecture;

[Manager]                     // shorthand
public class InventoryManager { /* ... */ }

[Layer(LayerId.Manager, Name = "Inventory Manager", Description = "Inventory business logic")]
public class InventoryManager { /* ... */ }   // exactly equivalent, with editor metadata

A layer attribute targets classes and interfaces only: structs, enums and delegates are not tracked. It is not inherited, so a subclass does not get its parent's layer, and a type belongs to exactly one layer.

Assembly-level tagging

When every type in an assembly belongs to the same layer, tag the assembly once in an AssemblyInfo.cs at its root. If a few types differ, override them with a type-level attribute.

AssemblyInfo.cs
using Tutan.Architecture;

// All types in this assembly are treated as Engine-layer...
[assembly: AssemblyLayer(LayerId.Engine)]

// ...except this one, whose type-level tag wins
[Layer(LayerId.Manager)]
public class CoordinatingManager { /* ... */ }

Resolution order

StepThe scanner findsResult
1[Layer(id)] or a shorthand on the typeThat layer (LayerResolutionSource.TypeAttribute)
2[assembly: AssemblyLayer(id)] on its assemblyThat layer (LayerResolutionSource.AssemblyAttribute)
3NeitherThe type is untracked: not scanned, not validated

Suppressing a rule

For an intentional, documented exception, put [SuppressArchRule] on the type. It may be applied several times to suppress several rules, and a family prefix such as "DONT" covers every finding in that family. Use suppression sparingly: each one is a reviewable exception to the architecture.

CheckoutManager.cs
[Layer(LayerId.Manager)]
[SuppressArchRule("DONT001", Reason = "This screen orchestrates a multi-step wizard; two managers are intentional.")]
public class CheckoutManager { /* ... */ }

Assign Layer from the Project window

Right-click a script and choose Assets → Architecture → Assign Layer…. The picker lists the five Löwy layers and puts the chosen shorthand attribute on the script's first type declaration, replacing a layer attribute that is already there.

Guides

Topology

In Löwy's Method the architecture is closed: every call passes through the immediately adjacent layer below. Skipping layers is a violation, upward calls are never permitted, and same-layer calls are forbidden. Each layer stays a complete abstraction boundary that can change without affecting the layers above or below.

The allowed directions

Read the matrix as "Can the row depend on the column?" Any pair without an allowed cell is disallowed, including the diagonal.

ClientManagerEngineResourceAccessResource
Client✗✓ (max 1)✗✗✗
Manager✗✗✓✓✗
Engine✗✗✗✓✗
ResourceAccess✗✗✗✗✓
Resource✗✗✗✗✗

Manager → ResourceAccess is the one skip: a Manager may reach ResourceAccess directly when a use case needs data without computation. The Client → Manager cap of one encodes Löwy's "one Manager per use case"; a Client that depends on two or more Managers is reported as DONT001.

Why same-layer is forbidden

Same-layer dependencies tie two components that share a volatility profile into a single unit of change, the hallmark of functional decomposition. If two Engines need coordination, a Manager orchestrates them (DONT011). If two data sources must be combined, a Manager decides which (DONT012). Clients are independent entry points, and each Manager owns one area of business logic.

Querying the topology

The topology is data: a list of TopologyCell entries in LowyTopology.Cells, queried through the shared LowyTopology.Instance. The rules read it, and so does the runtime container in com.tutan.hosting, so the two cannot disagree.

TopologyQueries.cs
LayerTopology topology = LowyTopology.Instance;

topology.IsAllowed(LayerId.Manager, LayerId.Engine);   // true
topology.IsAllowed(LayerId.Client,  LayerId.Engine);   // false: Client may not skip to Engine
topology.IsAllowed(LayerId.Engine,  LayerId.Engine);   // false: same-layer
topology.IsAllowed(LayerId.Engine,  LayerId.Manager);  // false: upward

topology.MaxCount(LayerId.Client, LayerId.Manager);    // 1 under Löwy's Method
topology.GetAllowedTargets(LayerId.Manager);           // { Engine, ResourceAccess }

Validation Rules

The validator runs a fixed set of rules against the scanned dependency graph. Every finding carries a rule id, such as DONT002, and the settings page shows each rule's plain-English Why and Fix.

Rule idSeverityWhat it checks
ARCH001ErrorEvery dependency follows the allowed directions of the closed architecture: no same-layer, skipping or upward edges.
DONT001WarningA Client depends on more than one Manager (Don't #1).
DONT002ErrorA Client depends on an Engine directly (Don't #2).
DONT004ErrorAn Engine accesses a Resource directly instead of through ResourceAccess (Don't #4).
DONT011ErrorAn Engine depends on another Engine (Don't #11).
DONT012ErrorA ResourceAccess depends on another ResourceAccess (Don't #12).
NAME001WarningThe type name ends with its layer's suffix: Manager, Engine or Access.
NAME002WarningEngines carry a gerund prefix; Managers and ResourceAccess must not.
ASMREF001Error.asmdef references between layer-tagged assemblies respect the topology.
STRUCT001Warning8 or more Managers: consider subsystems.
STRUCT002WarningThe Engine count exceeds the golden ratio for the Manager count.
STRUCT003InfoSeveral Managers but no Engines.
STRUCT004InfoMore than 24 tracked types.
Example findings
[Error]   ARCH001: disallowed dependency: GameClient [Client] → ScoringEngine [Engine] via ConstructorParameter
[Warning] DONT001: Client 'GameplayClient' depends on 2 Managers (SessionManager, LobbyManager). Don't #1: A Client should call only one Manager per use case.
[Error]   DONT011: Engine 'ScoringEngine' depends on Engine 'RankingEngine'. Don't #11: Engines must not call other Engines.
[Warning] NAME001: Manager type 'AuthService' should end with 'Manager'.
[Warning] NAME002: Engine type 'ScoreEngine' prefix should be a gerund (activity word).
[Error]   ASMREF001: Assembly 'Client.Gameplay' [Client] references 'Engine.Core' [Engine] which violates layer topology
Try a deliberate violation Give a [Client] a constructor parameter of an [Engine] type and run Validate Now. You should see ARCH001: disallowed dependency: GameplayClient [Client] → ScoringEngine [Engine] via ConstructorParameter. Fix it by introducing a Manager between them.

Validating from code

Scan the project into an ArchitectureGraph and run the fixed rule set from ValidatorFactory, for example from your own editor tooling.

ValidateFromCode.cs
using Tutan.Architecture.Editor;

var graph = new ArchitectureGraph();
graph.Scan(); // scans the project against Löwy's Method

var validator = ValidatorFactory.Build();
var results = validator.Validate(graph);

foreach (var r in results)
    UnityEngine.Debug.Log($"[{r.Severity}] {r.RuleId}: {r.Message}");

Settings & Enforcement

What you configure is only how loudly violations are reported. The enforcement mode lives on the FrameworkSettings asset at Assets/Resources/Framework/FrameworkSettings.asset, edited under Edit → Project Settings → Architecture. Without the asset, validation runs in WarningsOnly.

Enforcement modes

ModeBehavior
OffNo automatic validation. The menu item and the API still work.
WarningsOnlyEvery finding is logged as a warning. The default, for adoption.
ErrorsForCoreEach finding keeps its own severity: ARCH and ASMREF errors, naming warnings.
StrictEvery finding is logged as an error.
Adopt gradually Start in WarningsOnly to audit the project and fix the critical findings (ARCH001, DONT002). Move to ErrorsForCore to block on closed-architecture violations while allowing naming warnings, then to Strict to enforce everything.

After every domain reload

The CompilationHook loads the settings, exits if the mode is Off, scans the project, skips if no tracked types were found, then validates and logs each finding with its severity mapped by the mode. The format is [Architecture:RuleId] message (SourceType.FullName).

WarningWarningWarningError
ErrorWarningErrorError

CI / headless validation

CIValidator.Run scans and validates in batch mode, writes architecture-report.json (counts and a violations array) to the project root, logs each finding, and exits with code 1 if any Error-severity finding exists, otherwise 0.

CI pipeline
Unity.exe -batchmode -projectPath . \
  -executeMethod Tutan.Architecture.Editor.CIValidator.Run -quit

Wiring at Runtime

This package checks the code in the Editor. To construct the tagged types at runtime, hand each one its dependencies and start them in order, use the companion package com.tutan.hosting.

Its container reads the same LowyTopology the validator reads, so an edge the validator would flag fails the install with a named error instead of running. It requires the layer tag on every service it registers, so every service it runs is one the validator checks.
